# ViewModel migration (Voyager ScreenModel to AndroidX ViewModel)

> **Status: resuming.** Both halves of the deferral trigger are met: upstream shipped the migration in v0.20.2 and fixed its own `private` models in the same release. The inventory below was re-derived against the released code on 2026-08-06 and replaces the old `c3b99aea0` snapshot. The [durable approach](#approach-durable) and [durable lessons](#durable-decisions-and-lessons) survived the re-derivation intact; the counts and the phase split did not, and are corrected here.

## Goal

Take Mihon's migration off Voyager's `ScreenModel` onto AndroidX `ViewModel` (mihonapp/mihon#3594), across Reikai's own screens as well as the Mihon ones upstream's diff covers, and retire the `voyager-screenModel` dependency. No user-facing change; the payoff is staying on upstream's screen architecture so every later sync applies cleanly.

## Why

It is the one unported upstream change, and it is not a routine sync. Upstream removes the `voyager-screenModel` dependency, adds a `:core:viewmodel` module, and renames every `*ScreenModel` / `rememberScreenModel {}` to `*ViewModel` / `viewModel<T>()`. Reikai has its own screen models that upstream's diff does not cover at all, plus Mihon model files carrying `// RK` patches. Deferring it means every future sync of any screen file fights a base that no longer matches. That standing cost is the reason to do it eventually; the reason not to do it yet is in Status.

## Status

**Resuming, as of 2026-08-06.** The migration was attempted once on `feat/0.4.0`: the foundation, the leaf screens, and part of the browse cluster were built and verified on a minified `preview` build on-device. That attempt was reverted off the branch and preserved in a **local-only backup branch** (`backup/feat-0.4.0-viewmodel-migration`). It predates the released upstream shape, so treat it as a source of lessons, not of code.

**Both halves of the trigger are met.** The migration `c3b99aea0` shipped in **v0.20.2** (2026-08-01), with v0.20.3 and v0.20.4 on top; the `private`-model crash fix `98705910e` (mihonapp/mihon#3609) shipped in the same release. Take the fix wholesale rather than hand-widening an enumerated list to `internal`.

**The trip-wire also fired.** Waiting was not free. The old snapshot counted about 68 model files and 79 call sites; a cycle of Reikai screen work later it is 74 model classes and 72 call sites, with the Reikai-owned share up from about 33 models to 41. Every further cycle of screen work adds models the migration has to carry.

**Sync consequence, corrected.** The old wording said the synced base stays before the migration commit. It does not: `c3b99aea0` is an ancestor of the current synced base `45b1e781e`, because later commits were ported around it and the base advanced past it. Reikai is therefore already carrying an unported commit below its own base, which is the state the deferral was meant to avoid. [upstream-sync.md](../upstream-sync.md) carries the same correction.

**Sequencing, decided 2026-08-06.** The migration runs first, then the 33-commit upstream sync backlog lands on a matching base, then the content layer's history and updates redo. Three reasons: the redo's own files (`HistoryScreenModel`, `UpdatesScreenModel`) are renamed by the migration, so doing the redo first means doing that work twice and destroying rename detection on the files it just diverged; two of the redo's steps are already inside migration phases 5 and 7; and the sync's largest commit (`6d69903a5`, java.time to kotlinx.datetime) lands directly on the date handling both surfaces use.

The old sequencing note (library surface first) is spent: that surface shipped. Its claim that the port is "R097, about three percent, purely mechanical" was the best case quoted as typical and is corrected in [the inventory](#inventory-re-derived-against-v0204).

## Two layers, and which one to trust

Upstream's side of this is now fixed: v0.20.4 is released and the diff will not change under us. Reikai's side still moves, so the inventory below drifts every time a screen is added or a model is split. Re-run its counts before starting a phase rather than trusting a number written weeks earlier.

What does not drift is the reasoning: why a bare `viewModel<T>()` resolves without a factory, why a `private` one crashes, why per-screen scoping is free under Voyager, why the phases have to be vertical, and which of Reikai's own structures (the `MangaDexFollows` subclass, the drift-heavy library files, the merge code) are traps regardless of upstream's exact diff. Those are properties of AndroidX `ViewModel`, kotlinc, R8, and Reikai's architecture, not of any particular upstream commit.

## Approach (durable)

**The default factory does the work, and Reikai's Injekt pattern survives untouched.** A model whose constructor arguments are all Injekt defaults is resolved with a bare `viewModel<LibraryViewModel>()`, no factory. A model needing real arguments (a `mangaId`, a `sourceId`) gets a `companion object` holding typed `CreationExtras` keys plus a `viewModelFactory`, and the call site passes values through `extras`. A `Context` parameter comes from `Injekt.get<Application>()` instead of `LocalContext`. The replacement base is one file: `StateViewModel<S>` (`mihon.core.viewmodel`), a shape-for-shape stand-in for `StateScreenModel`. No shim and no typealias: a hard rename.

**Per-screen scoping is free, and needs no wiring.** `viewModel()` inside a Voyager `Screen` resolves to that Screen's own `ViewModelStore`, not the Activity's, because `voyager-navigator`'s Android variant hands every Screen an `AndroidScreenLifecycleOwner` (which implements `ViewModelStoreOwner`, provides `LocalViewModelStoreOwner`, and clears the store on pop). This holds only under a Voyager `Navigator`: content hosted outside one falls through to the Activity store silently. `ReaderActivity` and `WebViewActivity` are outside one and are unaffected, because `ReaderViewModel` is deliberately Activity-scoped via `by viewModels()` and `ReaderSettingsViewModel` stays a manual `remember { }` construction (it takes lambdas, so no factory is possible).

**Phases are vertical, one screen cluster at a time.** Reikai's models are constructed inside Mihon files (a Mihon tab builds a Reikai novel model, a Mihon queue screen builds both queue models), so "all Mihon files, then all Reikai files" cannot compile in between. Each phase takes the Mihon model, the Reikai models it constructs, and every call site together. The two systems coexist throughout (both dependencies present, some models migrated and some not), which is what allows phasing; `voyager-screenModel` drops only at the end.

**Each cluster is one commit, compiled, spotless-clean, and opened on-device.** A green build does not prove a screen opens (the `private`-model crash below compiles fine and dies on tap), so every migrated screen is exercised on a minified `preview` build before its phase is called done. Commits cite the upstream PR and the migration commit SHA.

## Durable decisions and lessons

These are the findings worth carrying forward verbatim; none depend on upstream's exact diff.

- **R8 needs no new keep (proven).** AndroidX's shipped consumer rules keep only `<init>(SavedStateHandle)` and `<init>(Application, SavedStateHandle)`; a `-keep class mihon.**` preserves the class, not its members. A bare `viewModel<X>()` on an all-Injekt-defaults model resolves through the reflective `SavedStateViewModelFactory` to a no-arg constructor that nothing keeps, so the risk was real. It was settled directly on the reverted attempt: the minified `preview` pilots opened cleanly and `dexdump` on the preview APK confirmed the no-arg constructors survive. Reikai's existing `ReaderViewModel` survives only by accident of shape (`@JvmOverloads constructor(savedState: SavedStateHandle, ...)` generates exactly the kept constructor). Re-confirm on the first minified build when resumed, but no keep is expected; if one is ever needed it is one line, `-keepclassmembers class * extends androidx.lifecycle.ViewModel { <init>(); }`.
- **A bare-`viewModel<T>()` model must never be `private`.** The default factory instantiates reflectively from `androidx.lifecycle`, and a private top-level Kotlin class is package-private in bytecode, so `newInstance()` throws `IllegalAccessException` the moment the screen opens. This is **not** an R8 trap: the modifier comes from kotlinc, so it fails on every build type, debug included, and a green build hides it. The fix is one word: widen to `internal` (public in bytecode, still module-private in Kotlin), marked `// RK`. An explicit factory is the other valid fix, and is what upstream already does wherever a model takes arguments, which is why only the no-arg ones break. Upstream currently ships this bug on several of its own no-arg models (`CreateBackup`, `ClearDatabase`, `MigrateDialog`, `More`, and at least `MigrationConfigScreen.ViewModel`, with more likely), so taking such a file verbatim imports the crash. Upstream has since fixed it in mihon `98705910e` (mihonapp/mihon#3609), which only drops the `private` modifier from the affected models: take that wholesale rather than hand-widening an enumerated list to `internal`.
- **`flowWithLifecycle` cannot survive inside a ViewModel.** A ViewModel outlives the composition, so a `Lifecycle` captured from it is the dead Activity's after a rotation. Upstream removed all of its `flowWithLifecycle` calls for this reason. Reikai's own instances are the custom-info overlay and the gallery-metadata flow, both cheap and self-triggered, so dropping the lifecycle parameter is safe; the flows then collect until the Screen is popped rather than pausing on navigate-away. The one flow worth watching is any chapter-list combine that takes `downloadCache.changes` / `downloadManager.queueState` unfiltered, since it re-fires on app-wide download activity; if that measures as real, scope those two inputs to the open entry (as the download flows already are) rather than reintroducing a lifecycle. Rejected alternatives: `ProcessLifecycleOwner` (a permanent divergence in the hardest-to-merge file) and `stateIn(WhileSubscribed)` (rewrites the worst file's state model and diverges from upstream forever).
- **`ioCoroutineScope` is deleted, per upstream's own rule.** It was `Dispatchers.IO`; `viewModelScope` is `Dispatchers.Main.immediate`. Rewrite the sites that launch real work to `viewModelScope.launchIO` and the `stateIn` / `cachedIn` sites to plain `viewModelScope` (their scope only hosts collection; the flows do their own IO). This is compiler-enforced: `ioCoroutineScope` is an extension on `ScreenModel`, so it stops resolving the instant a class extends `StateViewModel`, and no site can be missed silently.
- **A subclass that overrides a parent model needs its own factory.** Kotlin companion objects are not inherited, so a model that extends another and overrides methods (Reikai's `MangaDexFollowsScreenModel` extends `BrowseSourceScreenModel` and overrides its paging + metadata hooks) will, if it leans on the parent's factory, construct the parent type and silently lose every override, with no compile error. Give each such subclass its own key(s) + factory. This is a property of Reikai's class hierarchy, so it applies whatever upstream renames the parent to.
- **Drift, not markers, is the real hazard in the big files.** Reikai's library and details models and tabs are well over upstream's length, so upstream's diff maps to them as a spec to re-lay by hand, not a patch to apply by line. Budget these as re-writes guided by the upstream diff, and drift-check the result against the upstream post-commit blob (only RK-attributable hunks may remain).
- **Merge code is out of scope for the surfacing pass.** The merge-system rebuild ([merge-system-rebuild.md](merge-system-rebuild.md)) replaces or absorbs the merge surfaces and is ground-up across both content types; roughly a third of the details model's Reikai lines are merge handling. Extracting them during this migration is work the rebuild discards plus a conflict handed to it. Likewise leave blocks entangled with Mihon's private state (merged-chapter init, group refresh, related-mangas loader, merge actions) and the deliberate `EntryDetailsUiState` coupling ([unified-content-ui.md](unified-content-ui.md)).
- **Surfacing buried Reikai logic rides this migration, it is not a separate sprint.** The blocks worth lifting out of Mihon files are exactly the ones the migration renames, so doing them in the same pass avoids a rename-plus-extraction commit that destroys rename detection. It is the `unified-content-ui` initiative applied to files that skipped it (shared leaf, per-type mapper, optional slots, net-new in `reikai.*`), which is explicitly exempt from the no-standalone-refactor rule when planned and sequenced.

## Inventory, re-derived against v0.20.4

Measured 2026-08-06 against `refs/mihon` at `68aa4b003` and Reikai at `d53563baa`. Reikai's numbers drift with every screen added, so re-run the counts before each phase.

### Upstream's shape

`c3b99aea0` is 91 files, 1503 insertions, 1091 deletions. It renames roughly 29 `*ScreenModel.kt` files to `*ViewModel.kt`, adds the `core/viewmodel` module (three files, of which `StateViewModel.kt` is an 11-line shape-for-shape stand-in for `StateScreenModel`), and **drops `voyager-screenModel` from the catalog and the bundle in the same commit**. Upstream could migrate atomically; Reikai phases, so both systems coexist here until the teardown and no upstream commit models that intermediate state.

**The port is not a uniform find-and-replace.** Rename similarity runs from 68 to 97. Seven files are substantial rewrites rather than renames: `MigrateSearchScreenModel` (68), `ReaderSettingsScreenModel` (73), `WebViewScreenModel` (75), `DeepLinkScreenModel` (80), `MigrateMangaScreenModel` (81), `UpdatesSettingsScreenModel` (84), `HistoryScreenModelStateProvider` (85). `GlobalSearchScreenModel` is a delete-and-add, not a rename, because its constructor lost its default argument values. `LibraryScreenModel` is the 97 the old plan quoted as typical.

**Several upstream renames are no-ops here**, because Reikai already deleted and manifested the file: the migration flow's models (`MigrationListScreenModel`, `MigrateSearchScreenModel`, `MigrateMangaScreenModel`, the config screen's embedded model), `MangaCoverScreenModel`, and `HistoryScreenModelStateProvider`. Check [off-path-manifest.md](../off-path-manifest.md) before porting any rename; a manifested path takes its change in the Reikai twin instead.

**The worked examples to copy.** Factory-needing: upstream's `MangaViewModel` companion, holding `CreationExtras.Key` values plus a `viewModelFactory { initializer { ... } }`, with the call site in `MangaScreen` passing `extras`. Bare: upstream's `CategoryViewModel`, no companion, resolved `viewModel<CategoryViewModel>()`. `ReaderSettingsViewModel` is the third shape: a plain `ViewModel()` taking lambdas, still constructed by hand because a factory is impossible, and still living outside any Navigator.

`98705910e` un-privates twelve nested model classes across nine files by deleting the modifier, no `internal`, no added factory. One file also renames its nested `ViewModel` class to `Model` to stop it colliding with the `androidx.lifecycle.ViewModel` import. At v0.20.4 upstream ships zero remaining private-and-bare models, so files taken verbatim are safe.

### Reikai's shape

**74 model classes across 66 files.** By owner: 41 `reikai`, 15 Mihon-patched (carrying `// RK`), 13 Mihon-clean, 4 `exh`, 1 `mihon`. By constructor: **38 bare** (every parameter an Injekt default) and **36 needing a factory**. The factory work is mostly Reikai's own and upstream's diff gives no template for it beyond the one worked example.

**72 `rememberScreenModel` call sites across 49 files.** Two pass a `tag`, both deliberate and commented (`EntryMigrateHost`, `EntryMigrateDialog`, keyed by content type to avoid a stale instance in a reusable dialog). No `rememberNavigatorScreenModel` anywhere. Roughly 31 sites pass real constructor arguments and become `CreationExtras` at the call site.

**The blast radius is wider than the model files.** 97 files reference a `*ScreenModel` type by name, because composables, adapters and behavior interfaces take models as parameters. Every one of those signatures renames. The heaviest are `ReikaiExtensionsTab`, `ReikaiUpdatesScreen`, `EntryTrackInfoDialog`, `ReikaiSourcesTab`, `EntryMigrationListScreen`, `ReikaiHistoryScreen` and `ReikaiMigrateSourceTab`.

**Nothing outside the app module.** No other Gradle module references a Voyager model, so the migration is app-module only.

**The catalog is missing both new dependencies.** `gradle/libs.versions.toml` has `lifecycle-common`, `-process` and `-runtime` only. Phase 0 adds `lifecycle-viewmodel` and `lifecycle-viewmodelCompose` and puts both in the `androidx-lifecycle` bundle.

### The hazards, located

- **`private` models: 16 exist, 3 actually crash.** The three resolved bare are `MoreScreenModel`, `ClearDatabaseScreenModel` and `CreateBackupScreenModel`, all Mihon files that `98705910e` already un-privates, so taking that fix removes the risk before it can exist here. The other thirteen take real arguments, so their factories construct them directly with no reflection: `RestoreBackupScreenModel`, `WorkerInfoScreen.Model`, `MangaNotesScreen.Model`, `NovelNotesScreen.Model`, `EntryMigrateDialogScreenModel`, and the eight models inside `EntryTrackInfoDialog`. Un-private them anyway, matching upstream, rather than reasoning our way to a narrower fix.
- **`MangaScreenModel` is the hardest file.** It takes `lifecycle: Lifecycle` in its constructor and has **eight** `flowWithLifecycle` sites against upstream's six. Two are Reikai additions with no upstream counterpart, and one of those wraps a combine over unfiltered `downloadCache.changes` and `downloadManager.queueState`, which re-fires on app-wide download activity. See the [ruling](#rulings-2026-08-06).
- **Four `onDispose()` overrides need an `onCleared()` equivalent**: `DownloadQueueScreenModel`, `EntryMigrationListScreenModel`, the migration search screen's model, and `NovelReaderScreenModel`. Missing one leaks a job with no compile error.
- **`ioCoroutineScope`: 9 sites in 4 files.** One does real IO (`SearchScreenModel`, a source-wide search fan-out) and needs `viewModelScope.launchIO`; the other eight only host flow collection and take plain `viewModelScope`.
- **Two abstract Reikai bases dodge the init-order crash with `stateIn(Lazily)`**: `EntryCoverScreenModel` and `BrowseSourceScreenModel` (for the `MangaDexFollows` subclass). Both must stay `Lazily`; switching either to `Eagerly` re-opens the crash.
- **Six subclasses override a parent model** and each needs its own factory, since companions are not inherited: `GlobalSearchScreenModel`, `MangaDexFollowsScreenModel`, the two cover models, and the two bulk-favorite models.
- **Four String-keyed models** take a plugin `sourceId: String` where upstream's equivalents take `Long`, so their `CreationExtras` keys are Reikai's to define: `NovelBrowseScreenModel`, `NovelDetailsScreenModel`, `NovelCoverScreenModel`, `EntryMigrationFavoritesScreenModel`.
- **`ReaderSettingsScreenModel` is manually remembered outside any Navigator**, so `onDispose` never fires today and its scope lives until the Activity tears down. Upstream keeps it hand-constructed; the leak is worth fixing while the file is open.
- **Four tests construct a model directly.** Three inject a dispatcher and are insulated from the swap; `NovelBulkFavoriteScreenModelTest` has no main-dispatcher rule and survives only because the methods it exercises never launch.
- **R8 was settled empirically** on the reverted attempt: `dexdump` on a minified preview APK confirmed the no-arg constructors survive under the existing package keeps. Re-confirm on the first minified build; no new keep is expected.

### Rulings (2026-08-06)

1. **The `MangaScreenModel` lifecycle change follows upstream first.** Drop the constructor parameter and all eight `flowWithLifecycle` sites as upstream did, then test hard, specifically for work continuing while the details screen is backgrounded and for the two app-wide download inputs re-firing. If that testing shows a real cost, fall back to scoping those two inputs to the open entry rather than reintroducing a lifecycle.
2. **The untagged cover-model dialog is fixed now, separately.** `EntryDetailsDialog` resolves its cover model with an untagged `rememberScreenModel` while being hosted from both `MangaScreen` and `NovelScreen`, which is the stale-instance trap its two migrate-flow siblings tag against. It is a real behaviour fix and does not belong buried inside a mechanical port.
3. **The upstream sync backlog runs after phase 6, in one pass.** Four of its commits are cheaper on migrated files, but mixing a feature port into a rename phase makes an on-device regression unattributable.

### Phase map

0. **Foundation and the R8 proof.** Copy `core/viewmodel` verbatim, add the two catalog entries and the bundle change, wire `settings.gradle.kts` and the app dependency, keep `voyager-screenModel`, then migrate two pilots (one bare from `reikai.**`, one factory-needing from `exh.**`), build minified and open both on-device.
1. **Leaf screens.** The marker-free Mihon files with no Reikai entanglement. Verbatim upstream blobs. Take `98705910e` here, so the three bare-private crashes never exist in Reikai's tree. Carries the first `ioCoroutineScope` removals.
2. **Browse cluster.** The browse-source and search models, sources, sources-filter, extensions, plus the Reikai riders: `ReikaiBrowseScreenModel`, the three `reikai*Tab` builders, `MangaDexFollowsScreenModel` (own factory), batch-add, metadata-view, and the novel browse / globalsearch / sources models. The four String-keyed factories land here.
3. **Library cluster.** The library, library-settings and category models plus the library tab, and the novel library / update-errors / preferred-sources models. Risk is drift, not markers: re-lay the big files against upstream's diff and drift-check the result. Verify both library view modes and both content types.
4. **Details and reader settings.** The details model with its id and from-source factory, plus ruling 1's lifecycle removal and its hard test. Also the cover and notes models, the reader-settings model, the novel details / cover models, the related-mangas model (the only Reikai model holding a `Context`), and the eight `EntryTrackInfoDialog` models, the largest single factory batch in the tree.
5. **History, updates, downloads, more.** The history, updates, updates-settings, more and stats models, Mihon's inert download-queue model, and Reikai's novel history / updates, both queue models and both bulk-favorite models. The content layer's `HistoryUiModel` removal and its `UpdatesUiItem` deletion fold in here rather than being done twice.
6. **Teardown, docs, ledger.** Drop `voyager-screenModel` once no `cafe.adriel.voyager.core.model` import remains, take upstream's `Navigator.kt` (which deletes the `ioCoroutineScope` extension and the last `ScreenModelStore` use), rewrite the docs below, append the sync ledger row, add one `Other` line to `CHANGELOG.md`, final minified build.

Phases 7 and 8 of the old plan (off-path debt, surfacing buried Reikai logic) are dropped from this initiative: the content-layer program absorbs both, and carrying them here would stack a behaviour change on top of a rename.

### How each phase is executed

Verbatim upstream blobs where the file is marker-free, hand-merge inside the `// RK` islands where it is not, drift-check every hand-merge against the upstream post-commit blob so only RK-attributable hunks remain, and open every migrated screen on a minified `preview` build before calling the phase done. A green build does not prove a screen opens.
