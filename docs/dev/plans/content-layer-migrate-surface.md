# Content-layer migrate surface (the unified migration flow)

> **Standing rules for every session working this surface.** The goal is "write once, both get" unless the content type genuinely doesn't support it; for the program context read [content-layer-architecture.md](content-layer-architecture.md) and [unified-content-ui.md](unified-content-ui.md) first. And hold the nullable-soup rule: divergent bits are typed capability slots, never nullable fields or boolean-flag combinations on shared models. Two companion rules live in content-layer-architecture.md's Decisions and bind here too: a shared component either derives a piece of state or does not own it (sharing the storage while each type interprets it its own way is the same defect wearing a different hat), and a behaviour test written for one engine gets its twin. The v1 flow broke that rule at the state level (a row of ten lifecycle booleans plus nullable payloads) and paid for it with eight audit rounds; v2's sealed cells exist to make that class of bug unrepresentable.

## Goal

One Reikai-owned migration flow (screens, step sequence, and orchestration) serving manga and light novels, so a migration change is written once and reaches both content types. This is the migrate half of the "migrate plus global search" surface of the content-layer program ([content-layer-architecture.md](content-layer-architecture.md): one shared behavior + UI layer over a neutral Entry vocabulary, built one surface at a time). Global search is deliberately excluded from the takeover (see Decisions).

## Why

The two migration flows diverged structurally, not cosmetically. A 2026-08-02 research pass (route enumeration + UI comparison + seam pricing, adversarially verified against code) found 11 manga routes and 9 novel routes into migration, and the step sequences differ at every joint:

- Single-entry fork: manga's config screen replaces into `MigrateSearchScreen` when exactly one id is selected and shows the migration list otherwise (the single-id short-circuit in `MigrationConfigScreen.continueMigration`, which also skips the options sheet); novels always go config to list.
- Flag moment: manga batch routes pick data flags in the pre-list options sheet, and the batch confirm dialog (`MigrationMangaDialog`) has no checkboxes; manga single routes never see the sheet, so flags come silently from prefs until the single-item dialog. Novels pick flags in the final confirm dialog on every route.
- Manual override: manga pushes `MigrateSearchScreen` and pops back via an `addMatchOverride` protocol, with a second-level `MigrateSourceSearchScreen`; novels expand an inline `OverrideSection` in the row.
- Safety chrome: manga has an exit-confirm `BackHandler` and a modal progress dialog; the novel list has neither.
- Visuals: manga renders two large cover cards per row with top-bar commit actions; novels render compact rows with a bottom Copy/Migrate bar. A 19-element UI comparison found 12 differences a user would notice as two different apps.

Upstream migration fixes reach manga only; the novel twin never receives them, which is how the divergence accumulated. The owner ruled a flow takeover (option A, 2026-08-02): the program's "write once, both get" rule is violated worst on this surface, and no smaller option removes the step fork (a UI-only takeover keeps the fork because the fork lives in orchestration; patching Mihon's flow in place via `// RK` islands maximizes sync tax on the highest-churn files).

## Approach

### The amendment: scope and hard lines

This is the third orchestration amendment to the content-layer program, after the two library ones, recorded alongside them in [content-layer-architecture.md](content-layer-architecture.md). It supersedes the migrate part of the "details, browse and migrate keep the original rule" sentences that close both library amendments there.

- The takeover owns pure UI plus orchestration: the flow files of `mihon/feature/migration/` (config screen + sheet, list screen + model + sub-dialogs + `MigratingManga`, the batch `MigrationMangaDialog`, the single-item `MigrateMangaDialog`; not the `list/search/` engines and not `MigrationFlag`, see below), the migrate-search screens (`eu/kanade/presentation/browse/MigrateSearchScreen.kt`, `eu/kanade/tachiyomi/ui/browse/migration/search/` including `MigrateSearchScreenModel`), the per-source favorites pickers (`ui/browse/migration/manga/MigrateMangaScreen.kt` + its model, `reikai/presentation/browse/migrate/MigrateNovelScreen.kt`), the two merge-group pick wrappers (`reikai/presentation/manga/MangaMigrationSourcePickScreen.kt`, novel's twin inside its migrate tree), and the whole `reikai/presentation/novel/migrate/` tree. Roughly 1400 pure-UI plus 1400 orchestration lines.
- The engine floor stays Mihon and synced, never reimplemented: `mihon/domain/migration/usecases/MigrateMangaUseCase.kt` (already `// RK`-patched for merge-group carry-over), `mihon/domain/migration/models/MigrationFlag.kt` (it types the persisted manga pref), `BaseSmartSearchEngine` + `SmartSourceSearchEngine` (under `mihon/feature/migration/list/search/`; engine by role regardless of directory), and every interactor and repository they call. `reikai/domain/novel/interactor/MigrateNovelUseCase.kt` stays the novel-side sink. A step that starts reimplementing what these do has gone too far.
- **This widens the never-manifest-an-engine-file rule again, deliberately**, as the library takeover did for `LibraryScreenModel`: the migration flow's ScreenModels (`MigrationListScreenModel`, the config screen's embedded model, `MigrateDialogScreenModel`, `MigrateSearchScreenModel`) are orchestration and get deleted + manifested with their screens. The library amendment established this widening in principle (recorded in content-layer-architecture.md); the off-path manifest's "a ScreenModel is never deleted" line carries no carve-out note yet, so step 5 writes the first one.
- Global search is out. `SearchScreenModel` and `GlobalSearchScreenModel` stay live and synced; that area takes roughly one upstream behavior change a year, and its add-to-library half is already Reikai-owned via `MangaLibraryAdder`. The new flow does not consume `SearchScreenModel` at all: its single-entry search screen runs on the flow's own search adapter (see the contracts below). `MigrateSearchScreenModel`, a small subclass serving only the flow, is deleted with it per the widening above.
- The migrate-tab source-list layer is browse-surface chrome, not flow, and is handled symmetrically for both types: `ReikaiMigrateSourceTab` (Reikai-owned, pushes both types), manga's `eu/kanade/presentation/browse/MigrateSourceScreen.kt` + `ui/browse/migration/sources/MigrateSourceScreenModel.kt`, and novel's `MigrateNovelSourcesScreenModel.kt` all stay live. They are absorbed only if the step-2 design pass redesigns the source list too; otherwise they are off every delete list.
- Replaced Mihon files are deleted and recorded in the off-path manifest ([off-path-manifest.md](../off-path-manifest.md); `MigrateSourceTab.kt` already has a row there, so only net-new deletions get rows). The manifest's sync check and hooks are the guard that surfaces every future upstream change to a deleted file at sync time.
- Accepted sync cost: `mihon/feature/migration` took ~18 upstream commits in the 12 months before the ruling, ~13 of them behavior fixes, the highest churn of any surface taken over so far. Each future fix on a taken-over file becomes a triage per the manifest procedure: applicable (hand-port the idea into the shared flow) or not applicable (patches a mechanism the unified flow no longer has; note it in the sync ledger, [upstream-sync.md](../upstream-sync.md)). Mechanical churn (the pending ViewModel rename, pref API changes) stops costing anything on taken-over files; manifest rows get repointed on upstream renames per the manifest's VANISHED rule.

### Ruled design picks (owner, 2026-08-02)

1. The count-fork stays. One entry selected: config's Continue replaces into a migrate-search screen (fans the chosen target sources out at once; tapping a result opens the migrate dialog). More than one: the migration list. The fork is per count inside shared code; both content types take the same branch, so cross-type uniformity holds.
2. Data flags move to the final confirm. The confirm dialog carries the flag checkboxes on every route, batch and single. Per-type flag adapters read and persist the existing prefs; no enum merge.
3. Search-tuning options stay a pre-list sheet, as Mihon has it on manga today: extra search query, deep search, prioritize by chapters, hide unmatched, hide without updates. These shape the search that runs while the list populates, so they cannot live at confirm. Extra query and the two hide toggles apply to both types; deep search and prioritize-by-chapters are content-gated (they run on the manga smart-search engine) until a novel equivalent is leveled up.
4. Override is inline plus a deep option: the novel-style inline expandable picker (query field + per-source result strip) as the quick path, and a pushed full browse picker for one source as the deep path. Both types have a browse screen to push.
5. The visuals are redesigned, neither side adopted wholesale: a design pass grounded in [PRODUCT.md](../../../PRODUCT.md) via the `impeccable` skill (`.claude/skills/`; it needs the owner in the loop, see step 2) picks the row anatomy, progress display, and commit affordances, keeping the best of both (novel's compact rows and red chapter-shortfall warning; manga's exit confirm and progress dialog).
6. Mixed library selections keep hiding Migrate (the deliberate gate in `LibraryTab`'s `onMigrateClicked`). The unified flow could lift this later since it owns both id spaces; out of scope here.

### The step-2 design note (locked 2026-08-02)

The owner-approved design for the flow's surfaces. An interactive HTML mockup of all five surfaces (click-through flow, content-type gating, the verb-once commit rule) lives at [assets/migrate-flow-mockup.html](assets/migrate-flow-mockup.html); open it in a browser. The prose below is the binding spec; the mockup is its visualization. Register: product, Restrained (PRODUCT.md); flat-by-default, tonal hierarchy, mono numerals for every count (DESIGN.md). Anchors: Things 3's checklist quiet, Raycast's dense rows, Cron's mono numerals. Anti-anchor: Mihon's dual-cover migration row. Theme follows the app scheme.

- **Config screen**: flat rows, no card grouping. Selected and Available as tonal sections; drag handle only in Selected; language as quiet metadata text, not a pill. **Available lists enabled sources only** (owner ruling; disabled sources are not offered as targets, consistent with the sources list's disappear-on-disable model). Continue is the single accent control on screen.
- **Tuning sheet**: the five options in one sheet, one tonal step above the screen. The novel-gated options (deep search, prioritize-by-chapters) are absent for novels with a one-line note, never disabled rows.
- **List rows, compact + expand** (owner ruling): at rest one line per entry: small cover, single-line title, a `source -> target` metadata line, mono chapter counts with the shortfall delta in the error color (paired with the minus sign, never color-only), a 48dp accept control (re-tappable to un-accept), overflow for Skip. Expanding a row reveals the compare view (both covers larger, side by side), the inline override picker (query field plus per-source result strips), and the pushed deep browse picker. Top bar shows mono `n / total` searched; the tuning sheet reopens from a toolbar action.
- **The verb is chosen exactly once, in the bottom commit bar**: outlined `Copy (n)` and filled `Migrate (n)` with mono counts, reachable one-handed. The confirm dialog then carries the flag checkboxes, the skipped count in mono, Cancel, and a single action button matching the chosen verb. No second Copy-or-Migrate choice in the dialog.
- **Progress**: a quiet modal (owner ruling over inline commit state): linear bar, mono `n / total`, Cancel. Blocking is deliberate; rows are being mutated. Exit-confirm guards back all the way through commit.
- **Search screen (single-entry branch)**: the shared global-search layout (`EntrySearchSection` plus the shared card rows) over the chosen target sources; tapping a result opens the migrate dialog. No new visual vocabulary.
- **States.** Row: searching (skeleton strip, not a spinner), suggested, accepted, overridden, no-match (quiet "no results" plus the override affordance), skipped (dimmed, restorable). Screen: all-searched enables the commit bar; commit progress; **partial failure keeps failed rows in place with an error line and a retry** (replacing today's logcat-only failure on both types); done pops with a snackbar count.
- **Content.** All strings through MR resources with plural forms (retires the hardcoded English); shared strings say "entries" or interpolate the type, never "manga" or "novel" nouns; mono numerals wherever a count renders; motion 150-250ms, state-response only, reduced-motion clean.

### The v2 architecture (locked 2026-08-03): upstream's machine, neutralized

The flow is built by neutralizing Mihon's pre-ViewModel migration machine, which is in-tree and byte-identical to upstream `ef1c52967` (verified by diff), rather than writing a new orchestration. What makes upstream's machine guard-free and what v2 preserves as law:

- **A row is a stable object, not a copied value in a list.** Each row owns immutable entry data, a detached per-row `SupervisorJob` scope (cancelling a row can never cancel the batch), and its lifecycle as sealed state cells collected inside the lazy item.
- **Three sealed cells per row, one orthogonal flag.** The search outcome (`Queued / Searching / NoMatch / Failed / Found(suggestion)`), the commit lifecycle (`Idle / Committing(verb) / Failed(verb, flags) / Migrated(target)`) and the user's acceptance (`Untouched / Accepted(candidate) / Declined`) are independent axes. Acceptance is its own cell rather than a nullable target because an accepted target can be a strip or deep pick, un-accept must restore the suggestion, and the hide toggles have to tell "never looked at" from "handed back"; carrying that second distinction as a null plus a keep-visible boolean is what step 7 removed. `skipped` stays an orthogonal boolean: the shipped UX dims in place and preserves the target, which upstream's remove-row semantics cannot express. Retry memory is payload on `Failed`, never parallel nullable fields. Whether the screen may finish is not on the row at all: the finish gate owns it.
- **One sequential driver over an immutable snapshot with loop-head revalidation** (membership, still-unsearched, scope alive). No mutex, no generation counter: a tuning change that affects the search (extra query, deep search, prioritize-by-chapters, the only three that do) cancels row scopes and builds new row objects, so a stale writer holds an orphaned reference. The hide toggles are pure filters over derived state and never trigger a rebuild.
- **No rendezvous event channels.** Completion, pick failure, and navigation are consume-once state; the v1 audits showed channels drop, replay, or park behind an off-composition collector.
- **One extractable commit function** (`resolve` then `migrate`) shared by the batch list, the per-row commits, and the single-entry dialog; the list wraps it with retry memory, the dialog with consume-once completion.

The flow lands under `reikai/presentation/migrate/flow/`, written once against small per-type adapters harvested from `backup/migrate-flow-v1` (the seam contract survived all eight v1 audits; nothing needed redesign). Six contract fixes are baked into the harvested version: flags are persisted once at confirm and passed as values, never written inside `migrate()`; `resolve()` is the only method a commit depends on having run, and is idempotent (resolved-ness is a property of the candidate handle, never a row phase, which is how the novel unresolved-until-commit constraint fits without a special case); `suggest()` enriches the winner only; `candidates()` fetches nothing beyond its one search page; `prepare()` uses `runCatchingCancellable`; invalid persisted keys fail loudly. `MigrationCandidate` gains an adapter-built `cover` payload and a `resolved` flag so the shared row renders without downcasting the handle. Row identity is the existing sealed `EntryId` (`reikai/domain/entry/EntryId.kt`); no new id scheme. The adapters are the only per-type code; per-type divergence (manga smart-match options, novel plugin warm-up and cover Referers) is typed capability slots on the seam, per the standing rules above. Contract responsibilities:

- **Source catalog adapter** (config screen + tuning sheet): lists candidate target sources for its type, exposes and persists the ordered selection. Manga: Mihon `Source`/`Long` ids, persisting `SourcePreferences.migrationSources`. Novel: `NovelSource`/`String` ids, persisting `ReikaiSourcePreferences.novelMigrationSources` (`reikai/domain/source/ReikaiSourcePreferences.kt`). Enabled-source filtering is the adapter's job (manga: enabled languages minus disabled sources; novel: `GetEnabledNovelSources`).
- **Search adapter** (list rows and the single-entry search screen): given an entry, a query, and a target source, returns candidate rows (title, cover, chapter count, url). Manga impl wraps the smart-search engines plus `NetworkToLocalManga` (engine floor; deep-search and prioritize-by-chapters live here, which is why they are manga-gated). Novel impl calls `NovelSource.searchNovels`. The shared migrate-search screen runs on this adapter, not on `SearchScreenModel`.
- **Flag adapter** (confirm + single-item dialog): exposes the flags applicable to its type and the current entry, reads and persists the per-type pref, and translates the checked set into its use-case call. Both prefs are int-backed but **the bit layouts differ** (manga serializes `Set<MigrationFlag>` via `getObjectFromInt` on `SourcePreferences.migrationFlags`; novels store a raw bitmask under `novel_migration_flags` via `NovelPreferences.novelMigrationFlags()`; custom cover and notes sit on different bits), so adapters map by flag concept and never copy bits. The concept sets are near-identical; step 3's first deliverable enumerates both enums side by side (including whether novels have a remove-downloads equivalent) and fixes the shared checkbox list. Per-entry conditionals (has custom cover, has downloads) come from the adapter; a flag concept genuinely unsupported by one type is hidden for that type, never shown disabled and never a silent no-op.
- **Commit adapter**: `migrate(current, target, replace, flags)` calling `MigrateMangaUseCase` / `MigrateNovelUseCase`. Nothing above the adapters touches either use case.

Shared screens step 3 builds over those adapters: the merge-group pick screen (replacing the two per-type wrappers; the shared `MigrationSourcePick` composable already renders both types), the per-source favorites picker (replacing `MigrateMangaScreen`/`MigrateNovelScreen`), the config screen (multi-select + drag order, Continue applies the count-fork), the tuning sheet (five options, capability-gated per pick 3), the list screen + model (per-row search, accept/override, inline + deep override, exit confirm, progress dialog, commit actions), the single-entry migrate-search screen, and the confirm/single-item dialog with flags.

What landed, in `6cfb8fdd8` (device-verified) and `2e2a8e395` (compile and unit-test green, device check pending):

- `MigratingEntryRow.Acceptance` (`Untouched` / `Accepted(candidate)` / `Declined`) replaces the nullable target and the pin. `Declined` is what the hide toggles read, so a row the user just acted on cannot vanish when a late search outcome or a late count arrives, which is the bug three earlier patches chased. `Accepted` carries its target, so "has one" and "which one" cannot disagree, matching upstream's `SearchResult.Success`.
- `CommitActivity` (`Idle` / `Batch(done, total)` / `Single(entryId)`) replaces the `isCommitting` + `singleCommitInFlight` pair that six model guards and two UI gates had to AND together; the progress dialog reads its counters off the `Batch` arm rather than a parallel dialog case. The single commit now marks the screen busy on the caller's thread, which closes the window where a tuning rebuild could swap a row out from under a live commit.
- `MigrationRowRules.actions()` is the single source of truth for a row's controls, and `status()` returns a sealed `RowStatus` so a failed search and a no-match cannot share a rendering.
- `MatchStrategy` replaces the `supportsSmartMatch` Boolean, and `MigrationCandidate.resolved` is gone: resolved-ness is a property of the adapter-owned handle, as this doc always said it should be.
- The ScreenModel takes its adapter, pick handoff and dispatcher as constructor parameters instead of resolving Injekt in a property initialiser, which is what made the driver, the claim and the finish gate impossible to unit test. They now have seven tests, the first this ScreenModel has had. Rows take the dispatcher too, moving their network work off the CPU pool onto IO.

**Step 8, the last three shared-cell splits (2026-08-04).** A whole-system audit of the migrate and merge
systems (six parallel auditors, every finding re-verified against code; report in `docs/dev/audits/`) found
step 7 had not finished the job: three more places still held two answers to one question.

- **`Disposition` (Untouched / Armed / Settled) is now the one reading of where the user stands on a row.**
  The hide toggles read the acceptance cell, accept-all read "not accepted", and the finish gate read
  "migrated or skipped", so each collapsed `Declined` differently. Declining a row therefore wedged the
  gate for the rest of the session (nothing later could resolve it) and the next accept-all silently
  re-armed the target the user had just handed back. Skipped and migrated rows now also survive the hide
  toggles, which they did not: a skipped no-match row vanished under hide-unmatched, taking its Restore
  with it.
- **The confirm dialog is folded into the activity cell** (`Activity`: Idle / Confirm / ExitConfirm /
  Batch / Single). Starting a batch set the commit cell and left the dialog cell alone, so the confirm
  dialog sat on top of the progress dialog for the whole commit with a live-looking button that did
  nothing and Cancel stranded behind it; on a partial failure it outlived the commit and its button would
  start a second batch over the rows that had just failed. This is the same pair-of-truths shape step 7
  removed for `isCommitting` / `singleCommitInFlight`; the dialog was simply missed.
- **The override picker joined `RowActions` (`canPick`).** It rendered off the row's own `expanded` flag,
  so a migrated row kept a picker whose every candidate was tappable and silently refused, with the
  overflow that could close it already gone. `toggleExpanded` now reads the same rule the screen renders
  under.
- **The finish gate lost its per-batch scan.** It was redundant with the committable and busy checks (an
  unresolved batch row is committable or busy by definition), verified by mutation, and it was the clause
  that treated a decline as unfinished business. `batchTargets` became a plain `batchRan` flag, so the
  gate no longer holds row references that a tuning rebuild can strand.
- **`Migrated` and `skipped` can no longer both be true.** A skip landing between a commit's claim and its
  read of the flag left a row dimmed as skipped while showing a migration that really happened, with skip
  refused from then on. The commit clears the flag as the row goes terminal, so the combination is
  unrepresentable rather than guarded against.

**Step 9, the audit's remaining medium findings (2026-08-04).**

- **`emptyReason` is computed by the one function that computes every other count.** The init block
  assigned `visibleRows` by hand and never called `syncCounts`, and a load that produced no rows breaks
  the driver out before it reaches one, so the screen rendered a blank list. `NoEntries` was as
  unreachable as the already-recorded `NoSources`.
- **A deep pick that cannot be applied now says so.** `MigrationPickHandoff.take` clears on read, so a
  pick that failed after being taken had nowhere to go: the row stayed as it was and the user was told
  nothing. `PickOutcome` (`Unavailable` / `SameEntry`) is the consume-once state the v2 law lists
  alongside completion and navigation and that was never built.
- **`peekCounts` is a peek again on the manga side.** It aliased `resolve()`, so tapping a candidate cost
  up to two network round trips and permanently wrote chapter rows for an entry the user had not
  committed to, multiplied by row count on a bulk accept. It now reads stored chapters, or asks the
  source once with `fetchDetails = false` and stores nothing, which is the bounded display-only read the
  seam documents and what the novel side already did.
- **Tuning options a content type cannot run are dropped at the seam.** `deepSearch` and
  `prioritizeByChapters` stayed plain Booleans on the shared model, kept honest only by the sheet hiding
  their checkboxes; a value set any other way was accepted, discarded, and read back as false after
  buying a full rebuild. `MigrationTuning.normalizedFor(strategy)` strips them once, where the model
  reads and compares.

Also from the same audit and fixed alongside: the migration engines' favorite swap and merge-group rewrite
are now one transaction (see [merge-component-consolidation.md](merge-component-consolidation.md)). Open

## Decisions & tradeoffs

- Takeover over parity-patching: options assessed were (a) full flow takeover, (b) partial UI-only takeover, (c) no takeover with parity fixes, (d) reshape Mihon's flow in place via `// RK`. (b) keeps the step fork because the fork lives in orchestration; (d) is maximum sync tax on the highest-churn files; (c) leaves the divergence permanent, and history shows the novel side never receives flow improvements. (a) accepted with the churn price stated in the amendment.
- Global search excluded: separable seam, negligible churn, already half-Reikai via `MangaLibraryAdder`. The flow's search screen runs on its own adapter so `SearchScreenModel` is never absorbed; only the flow-serving `MigrateSearchScreenModel` subclass goes.
- No pref or enum merges: per-type flag enums and source-list prefs stay as stored; adapters translate by concept at the seam (the bit layouts differ, so bit-copying is forbidden). Avoids a data migration for zero user benefit.
- Count-fork kept deliberately (owner pick): per-count branching in shared code does not violate cross-type uniformity; always-list was considered and declined for the single-entry friction it adds.
- Deep-search and prioritize-by-chapters stay manga-gated at first: they run on the manga smart-search engine; leveling novels up is future work, not faked in the shared sheet. **Owner ruling (2026-08-03): level the novel side up wherever the plugin host can actually support it**, rather than leaving `supportsSmartMatch` gated forever. The tuning-sheet slice decides per capability, and a capability novels genuinely cannot support stays a typed gate with a one-line note, never a disabled row.
- The bulk-migration-tuning gate for novels (5B in [content-parity-drift-and-collapse.md](content-parity-drift-and-collapse.md)) is partially superseded: the shared sheet gives novels extra-query and the hide toggles; the smart-matching half stays gated as above.
- The migrate-tab source list is out of the mandatory delete set: it is consumed by Reikai-owned `ReikaiMigrateSourceTab` and is a browse-surface artifact, not flow; absorbing it is a design-pass option, not a requirement.
- **v2 over v1 (2026-08-03): rebuild on upstream's architecture instead of continuing to patch.** v1 wrote a new orchestration whose row was ten lifecycle booleans plus nullable payloads on copied value objects; eight audit rounds of recurring defect classes showed the guards could not converge. v2 neutralizes upstream's proven machine (stable row objects, sealed cells, per-row scopes, sequential driver) and adds each v1 capability back as a separately audited diff. The alternative, a ninth repair round, was declined on the recurrence evidence.
- **Durable v2 rules, enforced by representation:** no boolean lifecycle flags on shared rows (sealed cells; the nullable-soup rule applied to state); no lock held while awaiting foreign code, and no lock at all in the row machine (identity-based isolation via new row objects replaces epochs); no rendezvous channels for user-visible outcomes (consume-once state); adapter fetch timing is contract, not convention.
