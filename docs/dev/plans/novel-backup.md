# Novel backup & restore

The novel twin of Mihon's backup/restore: favorited light novels (with chapters, read state, history, categories, tracker links, and cross-source merges) ride the same backup file as manga, alongside a record of which sources you had installed so the restore screen can list the ones to install.

For the user-facing architecture of backups (file format, what is and isn't included, sync), see [docs/guides/backups.md](../../guides/backups.md). For the features this backs up, see the [merge system rebuild](merge-system-rebuild.md) and [novel tracking](novel-tracking.md) plans.

## Goal

A restore on a fresh install reproduces the full light-novel library exactly as it was: the same novels, read positions, reading history, categories, tracker bindings, and merge groups, plus the sources needed to read them. Novels are first-class library content, so they live in the one backup file with manga rather than in a separate export.

## Why

Before this, a backup captured only the manga library. A user with a sizeable novel library had no way to move it to a new device or recover it after a wipe, while their manga came back intact. The light-novel vertical (domain, reader, downloads, merge, tracking) was complete, so backup was the last core piece: it serializes everything the earlier work added (history, tracker links, categories, merges, grouping). That ordering is also why it shipped last in the active sequence.

## Approach

Novels piggyback on the existing backup pipeline. Creating a backup walks the favorited novels and writes each one (plus its chapters, history, tracks, and category names) into the same `.proto.gz` file manga go into. On restore, it reads those entries back and rebuilds the novel library, matching each novel to one that may already exist or inserting a new one. Two things need special care: the sources (which aren't part of the library data) and the merge groups (which are stored by internal id, and ids change on restore).

**Proto classes (proto = Protocol Buffers, the compact binary format backups serialize to).** Each novel concept gets a backup model that mirrors its Mihon manga counterpart: `BackupNovel`, `BackupNovelChapter`, `BackupNovelTracking`, `BackupNovelHistory`, `BackupNovelCategory`, and (in `BackupNovelMerge.kt`) `BackupNovelMergeGroup`, a group serialized as a list of `BackupNovelSourceRef` (`{url, source}`) refs. Every field carries a `@ProtoNumber`. The novel classes are grafted onto the root `Backup` object in the 700 number range, fenced with `// RK`, so they sit clear of Mihon's own fields (1-106) and Komikku's (600/610) and won't collide if upstream or Komikku patches are pulled in later. The root fields are `backupNovels` (700), `backupNovelCategories` (701), `backupNovelMerges` (702), and `backupNovelUnmerges` (703). `backupNovelSources` (717) carries each novel source's name, the twin of Mihon's `backupSources` (101), so the pre-restore warning and the restore log can name a source that is not installed; a backup without it falls back to the source id.

**Creating the backup.** `NovelBackupCreator` builds the proto objects, and it and `MangaBackupCreator` are the two adapters of one driver (`reikai/data/backup/BackupEntryDriver.kt`), which decides which series are backed up and which parts each carries. It always adds merge-group members outside the library (written with favorite off), because the groups are always written and a restore resolves a member only against a row it restored (owner, 2026-09-24; `GroupMemberBackupConformanceTest`). `BackupCreator` streams both through one writer, gated by the same `BackupOptions` toggles as manga (no separate novel toggle, since novels are library content like any other). History rows come from a new query pair on `novel_history.sq`: one read for backup, one idempotent upsert for restore.

**Restoring.** `NovelRestorer` mirrors `MangaRestorer`: it does a match-or-insert by `url + source` (find an existing novel with that source-and-url pair, otherwise insert a fresh row), then re-links the child data by stable keys rather than by id, since ids are assigned fresh on insert: chapters by url, categories by name, tracks by tracker id, history by chapter url. Where a series is already on the device, the two restorers merge by one set of rules in `domain/src/main/java/reikai/domain/backup/RestoreMergeRules.kt`, pinned by `RestoreMergeConformanceTest`: the higher version's details win, a chapter keeps read and bookmark from either side and the further progress (a deliberate departure from Mihon, whose manga restore let any non-zero backup position win and so could rewind the device), and a bound track keeps the device's row, remote link included, and takes only a further chapter read (Mihon's rule since mihon 4b48a84ec). `BackupRestorer` runs the novel restore as a self-contained sequential job (categories first, then each novel, then the merges) so it doesn't race the parallel manga and preference restore jobs. After the restore settles, the novel category-id preferences (the library / update filters and the default category) are remapped by category name to the freshly minted ids, so a saved filter follows its category instead of going stale; see [category-schema-unification.md](category-schema-unification.md).

**Merge/grouping surviving id reassignment.** Merge groups live in the DB (the `merge_group` + per-type member tables), not preferences, since the [merge system rebuild](merge-system-rebuild.md). Internal novel ids are reassigned on restore, so a group is serialized into the backup as stable `{url, source}` refs (`BackupNovelMergeGroup` / `BackupNovelSourceRef`, read from `MergeGroupRepository.getAllMemberships`). `NovelRestorer.restoreMerges` resolves each ref to its freshly restored id and hands the groups to `RestoreMergeGroups`, which both types share and which writes each through `MergeGroupRepository.materializeGroup` in one transaction: the backup decides the group of every entry it names, and local members it does not name keep their own group while two or more remain. The unmerge concept was retired in the rebuild, so unmerge refs are no longer restored (the `backupNovelUnmerges` proto field stays declared only so older backups still parse). A pre-rebuild backup's id-keyed merge preference keys are still skipped on an App settings restore (`AppPreferenceCarry`) so their stale raw ids aren't written back.

Manga merges use the same `{url, source}` re-keying, since manga ids are reassigned on restore too. `BackupMangaMerge` holds `{url, source}` refs (root proto field 711; 712 and 703 are no longer written, and are read only from a 0.3.x backup, which lacks the stored-groups marker at field 718 and has its same-title groups rebuilt, see [merge-system-rebuild.md](merge-system-rebuild.md)), `BackupCreator` serializes each manga group off `getAllMemberships`, and `MangaRestorer.restoreMerges` resolves the refs and hands them to the same `RestoreMergeGroups` (covered by `MangaMergeBackupRoundTripTest`). The manga restore also runs categories first: `BackupRestorer` awaits the category job before the manga and app-settings jobs, because `MangaRestorer.restoreCategories` maps each backup category to a live one by name, so the categories must already be in the database or the entry falls into the Default category.

**Installed-sources follow-on.** A library is only useful if you can reach its sources, and Mihon backs up the extension *repos* but not which extensions you had installed. A restore installs nothing, though: a backup can be anyone's file, so it never decides what code reaches the app (owner ruling C1, questions Q2 and Q3 of the 2026-10-04 build plan). Instead the Restore screen lists, before the restore starts and beside Mihon's missing sources and trackers, every extension the backup had that this install lacks, for the user to install from Browse. `BackupFileValidator` builds that one list for both kinds:

- Extension apps: `BackupExtension` records the installed manga and novel extension apps (`ExtensionBackupCreator` writes them). The validator names each one whose package is in none of the four installed lists (manga and novel, loaded and not loaded), read past the adult-source gate, so an untrusted, failing or hidden app is not listed.
- Novel plugins: no new proto is needed. A plugin's install state (its canonical URL plus metadata) rides the App settings backup, beside the last-seen record of each source's name. A restore never writes the URL list or the metadata (`AppPreferenceCarry`), and the validator names each backed-up plugin installed here neither from the same URL nor, by plugin id, from another repo, by the name it last loaded under or else its script's file name. The plugin repos still restore with App settings, so the plugins are a tap away in Browse.

**Backward compatibility.** Older backups made before novels existed still restore: Protocol Buffers default any absent field (so the novel lists come back empty), and the backup validator does not version-gate, so a pre-novel file is accepted unchanged.

## Decisions & tradeoffs

- **Proto numbering in the 700 range.** Chosen to leave Mihon's existing field numbers (1-106) and Komikku's patch range (600/610) untouched, so a future upstream sync or Komikku-derived patch can't collide with Reikai's novel fields. Proto numbers are permanent once shipped (they're the wire identity of a field), so picking a clear, documented range up front avoids a painful renumber later.
- **Id remap via `{url, source}` refs instead of trusting stored ids.** Merge groups are stored by internal novel id, but ids are reassigned on every restore, so the stored ids are meaningless on the target device. Serializing each group as `{url, source}` refs and rebuilding against the restored ids is the only correct option. The cost is excluding the two id-keyed merge preference keys from the generic preference restore, so the raw (stale) values never get written; the rebuild owns those keys instead.
- **Match-or-insert by `url + source`, re-link children by stable keys.** Mirrors the manga restore exactly. It makes restore idempotent and merge-friendly: restoring onto a device that already has some of the novels updates them in place rather than duplicating, and child rows re-link by url/name/tracker-id rather than by the ids that just changed.
- **A restore lists extensions rather than installing them.** Mihon installs no extension on restore either, but it also never records which were installed. Reikai records them, so the Restore screen can name what to install, and leaves the install to the user, since a crafted backup could otherwise steer which apps and which plugin scripts arrive. That also retired the plugin revalidation gate: it checked restored plugin URLs against repos the same backup supplied, so it vouched for nothing, and it stalled every plugin load while any added repo was unreachable. Its flag key is skipped on restore and left unread, with no cleanup migration (Q24).
- **A backup opened from another app restores in that app's task.** Files starts `MainActivity` in its own task, where it is never the root, and Mihon's guard against the launcher stacking a second copy finished every such launch, so the Restore screen never opened (cut-build device check, 0.4.0 cycle). The guard now drops only the launcher's own launch (`reikai/util/LauncherIntent.kt`, a `// RK` line in `MainActivity`, pinned by `LauncherIntentTest`), so a repo link, the other `VIEW` filter on `MainActivity`, opens too. It is not routed through `DeepLinkActivity`'s hop into the app's own task, because the file's read grant belongs to the activity Files started, and finishing that hop could take the grant with it. Mihon carries the same guard unchanged.
- **Reikai's app-key carries run on the App settings path only.** Retired keys carried into their replacements, keys a shared backup must not set (JS snippets on, WebView dev tools, the installed plugin list and its records, the NovelList server address, the extension installer, keeping a chapter's own scripts, and any app-state key, extension trust among them) and the bypass-server address all live in `AppPreferenceCarry`, which `PreferenceRestorer.restoreApp` wraps around the generic write. They used to sit inside the generic write, which `restoreSource` runs too, so a Source settings entry could rewrite an app setting (the bypass-server address, and with it the saved login) even with App settings unticked. `restorePreferences` is back to upstream's shape plus the category translation. The carries now run before the write rather than in the backup's key order, so where a backup holds both a retired key and its live replacement, the live key wins.
- **Backward compatibility comes free.** Protobuf defaults absent fields and the validator doesn't version-gate, so pre-novel backups restore unchanged with empty novel lists. No version flag or migration was added to the backup format.
- **No separate novel backup toggle.** Novels are gated by the same `BackupOptions` as manga because they're first-class library content; adding a distinct toggle would be surface area for no real user need.
- **The check after writing a backup only reads it back.** Upstream's `BackupCreator` runs the restore screen's `BackupFileValidator.validate` on every new file and discards the answer. Reikai's `validate` also resolves every novel source, which loads each installed plugin and can fetch scripts and repo registries over the network, so that ran on every backup, the automatic ones included. `BackupCreator` calls `checkReadable` instead: the same streamed decode, so a malformed file still fails the backup, and no source or tracker lookup for either content type. `BackupFileValidatorTest` pins it with strict source managers.
- **A backup names its novel sources without loading the plugins.** The source-name list a backup carries (field 717) reads `NovelSourceManager.nameOf`, which used to wait on the first plugin load, so a backup from a cold start still evaluated every installed plugin after the post-write check stopped doing so. `nameOf` and `langOf` now answer from the registry as it stands, then the last-seen record every plugin install and load writes, then the id, and never load anything: one rule for every caller that needs only a source's name or language. A plugin never loaded on this device is named by its id until it is. The restore screen's `validate` still loads the plugins, because whether each novel source is installed is what it reports. `BackupCustomInfoConformanceTest` pins the backup half through a real `BackupCreator` whose novel source manager fails on any plugin load.
- **A plugin's captured site sign-in is a sensitive setting.** The site storage an LN plugin's WebView captures (`webview:local` / `webview:session` under the plugin's storage scope, see [ln-plugin-host.md](../ln-plugin-host.md)) carries its login, yet its key has no private prefix, because the plugin's JS reads it back by that exact key. `PreferenceBackupCreator` leaves it out of Source settings unless sensitive settings are included, through `isSensitivePluginKey`; the IReader extensions' storage scope holds only extension-chosen settings and is backed up as before. Manga has no WebView storage capture, so there is no manga half.
