# Details

## Purpose

The details page is the hub for one series: cover, backdrop and description, the chapter list, downloads, tracking, categories, edit info, merged sources, and the start of every read. Manga and light novels render the same page through one shared body, so a details change written once reaches both.

## How it works

### Screens, models and adapters

Two routes stay separate because each page resolves its own model: `MangaRoute(mangaId)`, drawn by `MangaScreen`, and `NovelRoute(novelId)`, drawn by `NovelScreen`. A details page is addressed by its row id for both types, so a listing that has no row yet stores one first, outside the library. Each screen builds its adapter and hands it to the one shared body, `EntryDetailsContent`. Every caller builds a page through `DetailsRoutes.kt`: `EntryId.detailsRoute`, a browse result's `EntryBrowseRow.detailsRoute` (a novel result stores its row through `NovelLibraryAdder.materialize` and opens by the new id, null when the row cannot be written), `NovelItem.storedDetailsRoute` for a listed novel outside a browse row (a migrate candidate), and `shows`, the identity check the migrate flow makes before replacing the page below. A tap opens through `rememberDetailsOpener`, which ignores a second tap while the first page is still being built and toasts when it cannot be; a caller that is not a tap (the global search's single-result replace) calls the primitive itself. `DetailsRoutesGuardTest` fails on a `MangaRoute(` / `NovelRoute(` construction or a `::MangaRoute` / `::NovelRoute` reference anywhere else in Reikai's code, which it reads as every file under `reikai/` and `exh/`, a Mihon file with a `RK: whole file` header, and in other Mihon files the `RK` islands, the statement under a note, and the lines a trailing marker fences (within four lines of it, up to a blank line); a Reikai-owned file outside `reikai/` and `exh/` is not covered. The two pages:

- `MangaViewModel` (Mihon's, `// RK`-patched, live and synced) behind `MangaEntryAdapter`.
- `NovelDetailsViewModel` (Reikai's) behind `NovelEntryAdapter`.

Both adapters implement `EntryDetailsBehavior`, the shared action contract (selection, mark read and bookmark, downloads, hide and unhide, chapter-number edits, categories, cover, edit info, tracker autofill, favorite, the merge actions, refresh), and map their model's state to `EntryDetailsScreenState` (`Loading`, `Loaded`). `Loaded` carries the neutral header state (`EntryDetailsUiState`), the chapter list (`EntryChapterListUiState` of `EntryChapterListItem.Chapter` and `Missing` rows), `hasActiveFilter`, `viewedEntryId`, the header's `EntrySourceState` (installed, local, missing) and the typed `EntryCapabilities`. The adapter is where every per-type reconciliation lands, so neither model is made to implement a Reikai interface: the manga adapter resolves neutral chapter ids back to `Chapter`, gathers manga's per-item selection flags, and fans the neutral filter call out to three TriState setters; the novel adapter resolves the String source id, backs per-chapter download state with the disk cache, and pre-formats progress.

Per-type actions that are not shared (opening the reader, the novel page selector, plugin reload, share intents) stay on the concrete screen or adapter, so the shared contract never rots into no-op methods.

The body, not the screens, decides the actions both types gate the same way: Migrate, the interval editor, Edit category and Edit info act on a library entry only, and the Tracking button opens the track sheet once a tracker is logged in, else tracker settings (`forState` and `trackingTap` in `EntryDetailsContent.kt`, over `EntryDetailsUiState.hasLoggedInTrackers`). A screen passes those callbacks ungated. The track sheet is a route, `EntryTrackSheetRoute`, drawn as an overlay over the page with its pickers on a navigator of its own, as upstream's is.

The body also makes the pushes both types make alike, from the page's own state (`withSharedPushes` in `DetailsPushes.kt`): a global search scoped to the entry's type, a library search and a genre (back-stack walks through `DetailsGenreSearch.kt`), browsing the viewed source, tracker settings, the viewed member's notes, and Migrate's source picker for the anchor. A screen has no field for those (`SharedDetailsPushes`), so it states only which source the page views (`DetailsViewedSource`: its key, whether it has a catalogue to browse, whether a genre goes through its filters) and the pushes that are its own: the reader, the related and preview hops, the metadata viewer, chapter text search, and source settings, which a novel opens as a sheet or a screen by its settings kind. Every source settings screen, from details, a catalogue or an extension's page, is built by `SourceKey.preferencesRoute()` (`SourcePreferencesScreens.kt`), which `DetailsRoutesGuardTest` holds to as it does to `DetailsRoutes.kt`. `DetailsPushesConformanceTest` runs each shared push for both types.

### Dialogs

`EntryDetailsDialog` is the union both types can fill: `EditInfo`, `Cover`, `ManageSources`, `DeleteChapters`, `SetFetchInterval`, `ClearDownloads`, `RemoveFromLibrary`, `ChapterNumber` and `RelinkSeries`. `EntryDetailsDialogHost` renders them for both screens. Dialogs one type alone has stay in that screen's own dispatcher (novels: `NovelChapterSettingsDialog` in `NovelDetailsDialogs.kt`, the page selector, word count), so the union never carries a case one side cannot fill.

### What the page shows

- **The viewed member.** On a merged series the header, description, notes, web actions and download gate follow the selected source chip, or the anchor under All (`shownEntry` in `HeaderSource.kt`; manga reads `shownManga` / `shownSource`). Tags follow the chip too, but under All (`headerNamesWholeGroup`) they are the series' as the library reads them, through `shownTags` over `seriesGenres`: the anchor's Edit info tags when set, else every member's, the anchor's first, each tag once ignoring case and spaces. Manga reads the members from `mergedMangaById`; novels watch each member's row (`groupMembers`, which also feeds `groupNovels` and the All view's download folder owner) apart from the chapter list, so a sibling's new tags arrive without a chapter change or a restitch. A gallery anchor keeps its namespaced chips from its own tags (`rawGenre`); the other sources' tags join the un-namespaced row (`MangaGalleryCapability.otherTags`). Custom info is stored per member, and Edit info writes the anchor's row, so a sibling chip's title, synopsis and tags take the anchor's overlay while its cover is its own, with its own row's cover address (`shownManga`, `shownNovel`): the image its cover viewer opens. Notes are stored per member, so a chip's Notes editor writes that member's row and the novel model watches a sibling chip's row as manga's does, for an edit to show on return. Favorite and categories always act on the anchor, so switching chips never moves library state. Chip flips go through `EntryMergeGroupHost.selectSource`, which refuses an id outside the group and a re-tap, and both models drop their selection through `EntrySelection.afterChipFlip`. The group, its chips and the picked chip are one cell (`GroupState`, `chipsOf`). Merging itself is [merged-series.md](merged-series.md).
- **Source state.** `chaptersDownloadable` (installed only) and `isCoverAnchored` derive from `viewedEntryId` and `EntrySourceState` rather than per adapter. A missing source warns in the header and `rowOffersDownload` hides the indicator and download swipe on rows with nothing on disk or queued. Novels mark a member missing through `novelSourceState` once its plugin lookup has run, so the page does not flash a warning while the host loads.
- **Web actions.** WebView, Share, Copy link, the tag copy and the assistant link come from one `EntryWebPage` (url, `SourceKey`, viewed `EntryId`), built by `Manga.webPageIn` (upstream's `HttpSource.mangaUrlOrNull` rule, which hides the actions when the extension throws) or `NovelSource.webPageOf`, held by each model in a `ShownWebPage` that asks the source only when the shown member changes, and turned into actions by `rememberEntryWebActions`.
- **Theme.** The cover's seed colour themes the page when `themeCoverBased` is on; the backdrop and gradient are `EntryInfoBox`.
- **Status** labels and icons come from `entryStatusRes` / `entryStatusIcon`; novels store SManga's codes (`NovelStatusCode`).
- **Capabilities.** `novelPageSelector` (a paged LN source: the page bar and sheet, named by `novelPageText`; sort and filter are page-scoped), `mangaPagePreviews`, `mangaRelatedCarousel` (inline or as an overflow action, a Settings choice) and `mangaGallery` (namespaced tags and the gallery card for adult sources).
- **Novel-only overflow.** Search across downloaded chapters (`NovelChapterSearchScreen`) and word count (`NovelWordCountDialog`, words split on spaces by `NovelWords.countSpaced`), both over the chapters a tap would open; manga chapters on disk are images, so manga has neither.

### The chapter list

- **Rows.** `chapterRowTitle` gives the number where the entry shows chapters by number and the name otherwise; `chapterRowDate` reads the `UndatedChapterDate` slot (manga "N/A", novels blank, because novel sources rarely date chapters); `progressWhileUnread` hides progress once the row reads as read, against the group's read flag. The reader's chapter sheet uses the same three rules.
- **Missing markers.** `ChapterGap.withMarkers` walks the displayed rows and counts only whole numbers the series has nowhere, from any of its sources, so a repost, swapped pair, filtered or hidden chapter makes no gap, a merged series' included; `ChapterGap.Present` is built from every chapter before hidden rows and filters drop any, and a paged novel's from every page stored, not only the one shown. The header's count covers what the markers would; each type's "Hide missing chapter indicators" setting hides the markers and zeroes that count, as upstream does.
- **Sort.** A tap on the sort page flips the mode shown or starts a new mode ascending (`ChapterSortPick.descendingAfter`); a novel still on the global default flips what it shows. Novel chapter settings render Mihon's `FilterPage`, `SortPage` and `DisplayPage`. "Set as default" with Apply to library writes every entry in one transaction on both types. Without it, other library entries keep what they show: a manga stores the default it was added with, and a library novel still reading the live default takes the old one as its own first (`SetNovelChapterFlags.awaitSetAsDefault`), pinned by `GroupChapterSettingsConformanceTest`.
- **Reading order.** Resume, download next N and mark previous read ask `ReadingOrder` (always ascending, so next advances whatever the display order). Mark previous read walks the rows the list shows (novels through `novelShownRows`). A tap resolves through `chapterToOpen`: a listed row, else the Resume pick, so Resume still opens a chapter the list hides.
- **Jumps.** Scroll to top, next unread and bottom (`rememberChapterJumps`) sit in the top bar, or last in the overflow under the Appearance switch. Next unread is the Start/Resume chapter; one the shown list lacks toasts like none. Its icon is a book, the custom `book_small` (Material's book scaled to the arrows' height), since the bookmark icon read as chapter bookmarks. The header count is total items minus chapter rows, so the chapter rows must stay the list's last items in both layouts. The Start/Resume button docks to the screen's left or right (`ReadButtonSide`, mapped to the scaffold's start or end by layout direction), by drag or by setting.
- **Hidden chapters** are keyed by `hiddenChapterKey` (source plus url), resolved by `resolveHiddenChapterView`, and left out of the list, resume and every bulk download on both types.
- **Selection.** `EntrySelection` with `rangeOrToggle` (a long press on a selected row drops it); `chapterSelectionOffers` decides bookmark, mark read and unread, download and delete over `ChapterMarks`, the same rule Recents uses; a row that draws no download control (`rowOffersDownload`) adds no Download (`Loaded.selectionOffers`). Mark unread reads stored progress, never the drawn label.
- **Downloads.** The toolbar dropdown and selection pick through `DownloadCandidates` (novels keep `selectChaptersForDownloadAction` for the dropdown). The first download of an entry outside the library offers to add it, once per screen, through `AddToLibraryOffer`. An explicit download clears the selection; the new-chapter download a refresh starts leaves it alone, on both types.
- **Refresh** is DB-first: the source is hit on first open with no chapters, or on pull-to-refresh. Either fetch reports a failure, or an unpaged source listing no chapters, through `refreshFailureMessage` in a snackbar over the stored row, for both types; pull to refresh retries, and a novel refresh loads a plugin that threw while loading again (`RunSources`). Only an id with no row opens the shared not-found page (`EntryDetailsScreenState.NotFound`, drawn by `EntryDetailsNotLoaded`) for both types, and an older build's novel intent, which names a url rather than an id, shows that page's message as a toast when no saved row holds the url; any other failed read takes the screen down, as upstream's does. Both screens decide between that page, the skeleton and the loaded page from the neutral state alone. Novels refresh through `refreshNovelFromSource` (see [library.md](library.md)), which also walks the page being viewed. A paged novel's page with no stored rows is fetched when shown, once; a failure shows the same snackbar, and picking the page again retries it.

### Edit info and custom info

`EntryEditInfoDialog` is one Compose dialog for both types, on the `AdaptiveSheet` host: cover preview, status, title, author, artist, cover URL, description, alternative titles (one per line), draggable tag chips ending in an Add tags chip (several at once, comma-separated, as SY takes them), Fill from tracker, Collate tags on a merged series, and Reset info, Reset tags and Reset all. A save runs non-cancellable. Edits are stored as a non-destructive overlay, `custom_manga_info` and `custom_novel_info` (both implementing `EntryCustomInfo`), never written to the source row, so Reset restores the source even offline. The overlay is display-only: details, library, Updates, History, Recents and the widget show it (`withCustomInfo`, `overlayCustomInfo`), while merge, grouping, sort, filter, tracker search and download folders read the raw source values. Backups carry the overrides on each entry at Komikku's and Yokai's field numbers (`BackupCustomInfoFields`), with the alternative titles on Reikai's own 806; the old 0.3.x root sections are read through `LegacyCustomInfo`.

**Alternative titles.** They are stored on the custom-info row (`alt_titles`, one per line through `LineListColumnAdapter`, null when empty), so Reset all clears them, a rename keeps them, a row holding only them is kept, and a restore of an entry's custom info replaces them with the rest unless the backup carries none, which keeps the device's (`restoredAltTitles`, through `SetCustomMangaInfo.restore` and `SetCustomNovelInfo.restore`), since a backup from before field 806 or from another app cannot say it has none. Both screens open the dialog through `editInfoDialog`, the one seed rule: the overlaid values with the stored titles, diffed against the raw entry, which has none; `EntryEditInfoUi.altTitles` has no default, since a builder that forgot it would save the row with them wiped. `overridesOver` trims and dedupes them. A series' other titles are one kernel, `seriesAltTitles` (`reikai/domain/entry/SeriesAltTitles.kt`): every member's raw title, the lead's included, then the stored ones, minus the main title, each once ignoring case and spaces, the first spelling kept. Its readers are the header line, library search ([library.md](library.md)) and migration's search ([migrate.md](migrate.md)); gallery metadata titles are a separate manga-only source none of them read. The header shows them under the title (`EntryHeaderUi.altTitles`, from each adapter over the members the view stands for, `altTitleMembers` in `HeaderSource.kt`: every member under All, else the viewed one, a standalone entry being its own only member, so a chip or an unmerged entry under an Edit info title still lists its own source's title), each one searching globally on a tap and offering the title's long-press menu.

Fill from tracker pulls title, author, artist, cover, description and genres from a bound tracker (`Tracker.getMangaMetadata`, `TrackMangaMetadata`), picking through `TrackerSelectDialog` when several are bound; enhanced (self-hosted) trackers are excluded. Every way a tag arrives (added, filled from a tracker, collated from the merge's other sources through `groupSourceTags`, which reads them through `seriesGenres`) appends through `appendTags` in `EntryTags.kt`, blind to case and to runs of dashes, underscores and spaces by the library's `tagKey`, keeping the existing tag's spelling, because the tags may be the user's own. A dragged tag lands where `tagDropIndex` says. While a tag is held the form's own scroll is off, since it otherwise tracks the same finger and takes over mid-drag; a drag also clears focus, since a focused field pulls the form back to itself.

The cover viewer (`EntryCoverDialog` over `EntryCoverViewModel`, with `MangaEntryCoverViewModel` and `NovelCoverViewModel`) offers Edit and Delete only where `canEditCover` holds: in the library (or a local manga), since removing an entry deletes its custom cover.

### Chapter numbers

Both syncs number a chapter list through one kernel, `recognizeChapterNumbers`, over Mihon's list recognizer (`ChapterRecognition.parseChapterNumbers`): a volume or season is never the chapter number, a number every similar name shares (a group's) is skipped, and a chapter whose name gives no number takes one from its neighbours within one volume (2, ?, 4 gives 3; 10, ?, 11 gives 10.5), a bonus after the newest one and a prologue before the oldest one. A number the source gives is kept. The recognizer reads newest first, so the novel sync hands it the plugin's list reversed, with a plugin's 0 as no number. Each novel chapter stores the number recognition starts from (`raw_chapter_number`: the plugin's own, -1 for none), so a page sync numbers the novel's whole stored list with its page in place, ordered by page then listing order, and renumbers a stored chapter on another page that now reads differently: a chapter at a page edge gets the number one list would give it, whichever page arrived first. The same pass stamps each row's `sourceOrder` with its place in that whole list, since a plugin's index restarts on every page and every reading order sorts by source order alone. A page never fetched has no rows, so it gives no context. A refresh renumbers stored chapters when their list reads differently, which restitches a merged group and leaves read state, download names (name and url) and tracker progress (only ever pushed upwards, on a read) alone. A new chapter is marked a duplicate of a read one by the numbers the same sync leaves stored chapters with (`chapterArrivals`).

### Chapter-number corrections

A user can correct a source's wrong chapter number ("Correct chapter number" in the selection overflow, one chapter selected, or by tapping the out-of-line mark). The corrected number is written on the chapter row, so every rule that reads a number (list, sort, gaps, next chapter, tracker pushes, the merged stitch) reads it with no rule of its own. `manga_chapter_number_override` and `novel_chapter_number_override` remember each correction keyed by owner and url (a re-listed chapter gets a new row id), with the source's number beside it. Both syncs apply the corrections before comparing (`appliedTo`) and record a source renumber (`updateSourceNumbers`), so clearing restores what the source says now. `EditChapterNumber` reads and saves for both models; a save runs inside `ReconcileMergedChapters.afterPass`. Backups write the corrected number where Mihon writes one and the source's number in its own field (`BackupChapter` 701, `BackupNovelChapter` 12); restore writes them back (`backedUpOverrides`).

`ChapterNumberHint.forOwners` marks a chapter out of line with its own source's list (never the merged list): rows chain into runs that break at a jump over 10, and a run of at most 5 rows whose neighbouring runs are within 10 of each other is marked, with the free whole number its neighbours leave as the suggestion. Side content (side story, extra, special, omake, epilogue, prologue, bonus, afterword, illustrations, and unlabelled rows a volume-labelled list interleaves), hidden chapters, and a copy listed in the wrong place (within 2 days of a same-numbered row and over 30 days from both neighbours) are never marked. An unknown date never decides.

## Invariants and traps

- **`MangaViewModel` is never made to implement the shared contract.** The adapter reads it and forwards; a renamed upstream field breaks `MangaEntryAdapter` at compile time.
- **Derive the rows, chips and picked chip from one snapshot.** Reading the chips from the live host while the rows came from an earlier snapshot wrote an ungrouped list under the merged switcher; both models carry the `GroupState` each list was built for and read the chips through `chipsOf` and the picked chip off that same group. The host's collector is the one chip resolver; a model that resolves its own runs the lookup twice per change and reopens the race.
- **Description expansion is a layout input too.** The two-pane layout opens the synopsis expanded; an adapter that drops that field shows it collapsed.
- **A one-shot flag on a rebuilt state does not survive.** `NovelDetailsState.Loaded` is rebuilt whenever the chapter list changes; the first-download prompt lives in `AddToLibraryOffer` for that reason.
- **A web page lookup in the adapter would run per download tick.** Resolve it in the model through `ShownWebPage`.
- **The custom-info overlay never touches the source row.** Tracker search, refresh, duplicate detection, download folder names and merge read raw values.
- **The partial novel update must be able to write null** for author, artist, description, cover and genre, which `RepairNovelDetails` relies on to clear a neighbour's details.
- **Every download control and bulk download reads one rule, `DownloadTargets.of`.** A row fetches its own copy while its source is installed, else an installed source's copy of its merged chapter, else nothing; with no stored stitch there is no other copy, so it is its own or nothing. The library, both readers, the All view and Recents build their targets through it with no gate of their own, so a row only an uninstalled source holds draws no control and no bulk action queues it. A details list showing one source keeps `DownloadTargets.OWN` and gates on that source through `offersDownload`'s `canFetch`, since its header already tracks whether the source is installed. Recents cannot tell a group with no stored stitch from a chapter the stitch has not placed (both fall back to `soloUnit`), and needs not to: the rule answers both alike. Pinned by `EmptyStitchDownloadConformanceTest`.
- **Download progress never enters the details state.** A tick writes `MangaViewModel`'s progress map, which only each row's indicator reads through `EntryDetailsBehavior.downloadProgress`, so it redraws a ring rather than rebuilding the list. `getDownloadProgress` resolves a row through its download target, so a merged row fetching a sibling's copy shows that copy's progress; novels answer `DownloadProgress.Unsupported`, the slot Recents rows read too.
- **A notes page carries who it notes, never the notes.** Android rebuilds a screen from its saved arguments after closing the app in the background, so a carried copy came back stale and the next edit saved over newer notes. Manga's page is upstream's `MangaNotesRoute(mangaId)` with its load-by-id `MangaNotesViewModel`; the novel's (`NovelNotesRoute(novelId)`) and a local volume's (`VolumeNotesRoute(type, series, volumeKey)`) read through `NotesEditor`, the volume heading itself with the chip `chipOf` derives as the series' page would. Each page closes when what it notes is gone, by one rule (`closeMissingNotes`): a series' notes close its details page below too, as upstream's manga page does, and a volume's leave the series page open, since the series may still be there. Pinned by `CloseMissingNotesTest`. An empty note is a volume with none written yet. Pinned by `NotesRestoreTest` and `NotesSaveConformanceTest`.
- **The list as shown is built with the neutral state, off Main.** The Only copies filter and both volume views (`DetailsVolumeViews`, as the files hold them and as the series shows them) are passes over every row, and the rows change on every download tick, so `neutralDetailsState` builds them on Default from each adapter's `DetailsVolumeInputs`. The Only copies switch is saved with the page (`rememberSaveable`), so it outlives the process as the page does, and handed to the adapter (`setOnlyCopies`). A page reading `chapters.items` where it meant the shown list draws rows a filter or a picked volume hides.
- **A volume move's follow-up runs on the model, never the composition.** Add volumes, Split out, Organize files, Delete volumes and the relinks, and the library's Combine as volumes, run through `VolumeMoves` on the model's scope over its snackbar, so a rotation or fold keeps the Undo, the toast and the hand-off to another series' screen, whose push waits for the live navigator (`PushOpened`). A coroutine from the composition was cancelled by the recreate, and the move's tidy then ran with no Undo offered. Pinned by `OrganizeUndoHandOverTest`.
- **A chip's cover and its cover viewer read the same row.** Both models subscribe to the selected chip's own custom-info row beside the anchor's, and `shownManga` / `shownNovel` take it only when it was read for that chip, so a flip never draws the previous chip's address.

## Decisions

- **One shared body, two screens.** A route carries identity only, so one screen through a lambda opener is out; the body is written once.
- **The merged display convention is the anchor.** `Loaded` carries one always-populated display entry plus a source name, so shared code has no null branch for "primary".
- **The corrected chapter number is written on the row**, not overlaid at read time, which would need every number reader to apply it. Keyed by owner and url, one table per type, so a merged series' other sources keep their numbers and a migration does not carry it.
- **Custom info is an overlay table, display-only.** A rename must not reshuffle or unmerge the library, and Reset must restore the source offline.
- **Genres from a tracker are appended, never replaced.** Only genre lists, never the noisy tag or category dumps (AniList tags, MangaUpdates categories).
- **Edit only where a custom cover is kept.** Letting an entry outside the library keep one would need an `// RK` change to Mihon's `editCover` and still orphan files.
- **A details page is addressed by row id; a listing open stores first.** Stored outside the library, as manga's browse already stores every listed row, so the page's first fetch updates that row like any refresh. A local import stores a novel either way, so the import list can open it; a manga imported outside the library has no row and its import row opens nothing, a gap that predates the rule.
- **The novel related carousel stays empty** until a novel recommendation source exists.
- **The Upcoming screen and the interval library filter stay manga-only**, by ruling rather than mechanism: novels predict `next_update` through `ReleaseInterval` and share the Set-interval dialog.
- **Tag chips stay Mihon's flat outlined `SuggestionChip`.** Its outline keeps contrast under AMOLED; Komikku's filled chip would need an AMOLED branch.
- **Word count splits on spaces** as Tsundoku does, so a Chinese or Japanese chapter reports few words.

## Extending

- **A new action**: add it to `EntryDetailsBehavior`, implement it in both adapters, render it in `EntryDetailsContent`. A type that cannot do it leaves it hidden through state, never a no-op.
- **A per-type section**: add a typed slot to `EntryCapabilities`, filled by the one adapter that can.
- **A new shared dialog**: add a case to `EntryDetailsDialog` only if both types can fill it; otherwise keep it in that screen's dispatcher.
- **A new chapter-row rule**: put it in the row kernels so the reader's chapter sheet follows.
