# Syncing with Mihon

Reikai is built on [Mihon](https://github.com/mihonapp/mihon) but is a standalone repository, not a GitHub fork, so there is no upstream remote to pull from. Upstream changes are ported **by hand** from the local `refs/mihon/` reference clone. This doc is the process, the commit convention, and the running ledger of where Reikai sits relative to upstream.

## Why by hand

`refs/mihon/` is a read-only reference clone, not a remote, so there is nothing to pull. And Reikai has diverged: `// RK` islands patch Mihon's own files, large areas are re-typed onto Reikai's models (Compose/Voyager, immutable domain), and the novel and adult code is net-new. Each upstream change is re-applied by hand and re-targeted to Reikai's shape. Model the cost as a per-change re-targeting cost.

## How to sync

1. **Find the new commits:** `git -C refs/mihon log --oneline <last-synced>..HEAD` (the last-synced SHA is the top ledger row below). Pull `refs/mihon` first; the clones live in the parent dir `refs/`, not inside `app/`.
2. **Check off-path files:** `pwsh scripts/off-path-check.ps1 -MihonBase <last-synced>`. It fails if the range touched any file in the [off-path manifest](off-path-manifest.md) (a deleted Mihon UI file whose twin Reikai renders); reconcile each flagged change into its replacement twin by hand. The diff is upstream-side, so a reported path stays reported however well you reconciled it: once you have walked each one, re-run with `-Reconciled` to write the stamp the `commit-msg` hook wants. A pass that stops below upstream HEAD, because a commit in the middle is deferred, adds `-MihonThrough <sha>` to bound the range at the point it reaches; the stamp then records that SHA and every commit in the pass has to cite it.
3. **Port each commit** by the [method](#porting-method): verbatim-copy marker-free files, hand-merge `// RK` files.
   - **A Weblate import is a scripted per-key three-way merge**, never a wholesale copy: take upstream's value for a key only where Reikai's base still declares it and Reikai's own value has not diverged from the pre-sync one, so the debrand and the deliberate string divergences survive. Drop the keys upstream removed that Reikai's base no longer declares either; they are dead weight left by an earlier port. Re-parse every touched file as XML and re-check that no incoming value reintroduced upstream's branding.
   - **A locale upstream gains is a locale Reikai takes, empty or not.** Translations come from upstream and there is no capacity here to write them, so a locale is never skipped. An empty file was skipped twice on the belief that it would list the language in the system picker with nothing behind it; measured on this tree, that does not happen. moko-resources generates no `values-<lang>` folder for a file with no `<string>` entries, and the generated `locales_config.xml` lists only the locales that produced one, so an empty locale is inert and reaches no picker. Take every locale on the sync that adds it, and let it fill in later.
4. **Drift-check** the hand-merges, then list unfenced edits: `pwsh scripts/rk-fence-report.ps1 -MihonBase <new base>` diffs every file Reikai shares with `refs/mihon` against that base and prints each changed hunk no `// RK` marker covers, plus any RK marker in a Reikai-owned file (rule: `.claude/rules/architecture.md`). It is a heuristic report wired into no hook, and the tree carries a backlog, so fence what the pass touched rather than expecting a clean run. Audits run it the same way against the top ledger row.
5. **Compile** (`:app:compileReleaseKotlin`) and on-device verify anything user-facing.
6. **Commit** with the [convention](#commit-convention).
7. **Append a ledger row** recording the new base and what was ported or skipped. Add it at the top and open its Base cell with the SHA in backticks, `(unchanged)` included: `Get-SyncedMihonBase` in `scripts/mihon-ownership.ps1` reads that cell as the synced base for `dup-check.ps1` (the pre-commit hook and CI), which decides which files are Reikai's. One line per row; the sync commit body carries the detail.

Port every new commit by default. Only skip one for a concrete, defensible reason (it re-implements something Reikai deliberately rewrote and would contradict live behaviour, or it is N/A like a Mihon version-code bump). Surface a skip as a choice, never decide it silently.

## Commit convention

Reference upstream PRs/issues as **`mihonapp/mihon#<n>`** (a cross-repo link). A bare `#<n>` auto-links to a *Reikai* issue and is rejected by the docs lint. Cite the upstream short-SHA too, and use `chore:`, never `feat`/`fix`.

- **Subject:** `chore: sync Mihon <what> (mihon <sha>, mihonapp/mihon#<n>)` for one commit; `chore: sync Mihon <theme>` for a batch.
- **Body:** lead with what changed and why it matters, one bullet per ported commit, note any skip with its reason. Keep it concise; the deep porting mechanics live in this ledger, not the commit.
- No em dashes, no AI watermarks (see [code-quality.md](../../.claude/rules/code-quality.md)).

## Porting method

- **Marker-free file (no `// RK`):** copy the upstream post-commit blob verbatim. Confirm Reikai sits at Mihon's pre-commit base first (`diff` the file); a clean match means the copy is safe.
- **`// RK`-patched file:** re-apply the upstream hunks by hand around the RK islands. Never let an upstream change land inside or clobber an island.
- **Whole-file rewrite (a `// RK: whole file, <why>, see <doc>` header in its first lines):** hand-merge the upstream change into the rewrite as a whole, reading the file's row in [Deliberate divergences](#deliberate-divergences-from-upstream) first. The header replaces islands, so `scripts/rk-fence-report.ps1` lists the file without checking its hunks. A new rewrite gets the header and a row in the same commit; where no Mihon file imports it, move it into a Reikai-owned file and delete and manifest the original instead.
- **Pure deletions stay unmarked.** Upstream code Reikai dropped with nothing replacing it carries no note; the diff before a verbatim copy shows it, and `scripts/rk-fence-report.ps1` reports it as an unfenced removal. A member moved elsewhere keeps its one-line `// RK:` note naming where it went ([architecture.md](../../.claude/rules/architecture.md)).
- **Drift-check:** `diff` each hand-merged file against the upstream post-commit blob. A faithful port leaves only RK-attributable hunks (an RK island, an RK-supporting import, an RK-fenced line). Any other hunk is drift, a dropped or mis-applied change.
- **Collapsing a Mihon file onto a Reikai twin: delete pure-UI, keep engine + partial.** When a Mihon file's UI is *fully* replaced by a Reikai-owned twin (`reikai.*`), **delete** the Mihon original and record it in the [off-path manifest](off-path-manifest.md), rather than keeping a dead copy an edit might silently land in. The `refs/mihon` clone holds the pre-delete blob as the diff base, and the manifest's sync check (`off-path-check.ps1`, step 2 of [How to sync](#how-to-sync)) fails loudly if upstream later changes the file. Two things stay live, never deleted: an **engine** file (a ViewModel, repository, source manager) is minimally patched on the render path (e.g. `LibraryViewModel`, live behind the library adapter), with a ruled orchestration takeover as the only exception, recorded in the manifest's carve-out note; and a **partially collapsed** file keeps its live remainder in place, marked `// RK` with what moved out, and is manifested only once nothing live remains.
- **Review for it:** the manifest is the enforcement, but a *new* reroute that skips it is invisible. Whenever a sync or a feature reroutes a Mihon file to a `reikai.*` twin, add it to the manifest (or the next sync silently misses upstream's change to it). Periodically audit for un-manifested reroutes with `git log -M20% --find-copies-harder --name-status` over the whole source tree: `git` records a move as a rename only above its 50 percent similarity default, so a heavily rewritten twin reads as an unrelated delete plus add, and a pathspec limited to `eu/` cannot pair a rename landing in `reikai/` at all.

  A cheaper audit answers the same question without relying on rename detection: list every file in the
  `refs/mihon` tree, subtract the ones that exist here, and subtract the manifest. Anything left is a reroute
  nobody declared. The expected leftovers are Mihon's own launcher icon, logo and splash (replaced by
  identity), files upstream also deleted, and renames; a sync never justifies a skip on the grounds that
  Reikai no longer has the file.

- **Reconciliation is a separate pass from the manifest.** The manifest proves a change was *reported*; only
  reading the twin proves it was *carried*. For each reported path, compare the upstream hunks against the
  twin, and expect a hunk to sit one file over from the row's Replacement, which is an entry point rather
  than an address.
- **A large cross-cutting commit is bucketed before it is ported.** For each path in
  `git -C ../refs/mihon show --name-only --format='' <sha>`, compare this tree's file with
  `git -C ../refs/mihon show "<sha>^:<path>"`: identical means take upstream's post-commit blob verbatim,
  different means hand-merge, absent means check the [off-path manifest](off-path-manifest.md). Then list the
  Reikai-owned files forced along by finding callers of every signature the commit changes, not by grepping
  for the imports it touches, which over- and under-reports. A novel twin of a converted manga file gets the
  same change even when it still compiles, or the two drift.

## Recurring gotchas

- **The EXH-override tax:** changing a Reikai-`open`ed `source-api` method breaks Reikai's two EXH overrides (`exh/source/DelegatedHttpSource.kt`, `EnhancedHttpSource.kt`, absent from Mihon). Re-type both overrides too.
- **Migration numbers diverge:** never copy Mihon's `.sqm` number; Reikai's sequence is ahead. Add a new Reikai-numbered `.sqm` with the same schema change.
- **Root `spotlessApply` is safe.** The tree is clean, so it should touch only your own changes. Check `git status` after running it: CI runs root `spotlessCheck`, so any other file it touches is a real block.
- **Version and release commits are N/A:** Reikai keeps its own `app.reikai` identity and version numbering, so skip Mihon's version-code bumps and release-artifact commits.
- **CI-action bumps go to Reikai's own workflows:** Reikai owns `build_check.yml` / `nightly.yml` / `release.yml`; apply an action bump there, not to a Mihon `build.yml` Reikai lacks.
- **Coupled bumps land together:** a major dependency bump and its deprecation-fix commit must ride one commit (e.g. xmlutil 1.0.0 with its `XML.v1` migration), or the first commit will not compile.
- **Three upstream rules now live in Reikai kernels both content types call**, each reached from a `// RK` island: the Smart update skip `when` in `LibraryUpdateWorker` (and the three restrictions `StatsViewModel` counts) is `reikai.domain.library.smartUpdateSkip`, the last-read and start-date backfill in `AddTracks.bind` is `reikai.domain.track.bindBackfill`, and the added-chapter rules in `SyncChaptersWithSource` (fetch-date stagger, mark duplicate read, re-added chapter inheritance) are `reikai.domain.chapter.chapterArrivals`. An upstream change to any of those blocks lands in the kernel, not in the island, so the novel side gets it too.

## Deliberate divergences from upstream

Cases where Reikai knowingly does not match `refs/mihon`, so a future syncer does not "fix" them back. Revisit each when upstream settles.

- **`GetApplicationRelease.isNewVersion` compares versions position by position, where upstream's loop is wrong three ways.** Upstream walks the installed version's positions and indexes the release tag by them, so a longer installed version throws `IndexOutOfBoundsException` (which is why a Yokai-era five-segment build was never offered an update), a segment the tag adds is never examined, and any later position being greater returns true, so `0.3.9` reads as newer than `0.4.0`. Ours pads the shorter list and stops at the first difference. Fenced `// RK`, covered by three cases in `GetApplicationReleaseTest`. Not reported upstream; drop the island if a sync brings an equivalent fix.
- **`source-api/consumer-proguard.pro` keeps `ConfigurableSourceKt` and `ConfigurableSource$DefaultImpls` with their public members, which upstream's list omits.** Extensions built on older libs call `preferenceKey()` and `sourcePreferences()` from those two classes, and nothing in the app does, so once mihon `06d612811` dropped the package keeps R8 deleted `ConfigurableSourceKt` outright; the `DefaultImpls` default had already been stripped before that, because a class-only keep never kept members. Both lines sit in the `// RK` island. Upstream ships the same gap, so the fix is to be offered there. Drop the two lines if a sync brings an equivalent keep.
- **The details screen's non-global search walks the back stack, where Mihon looks one screen back.** Mihon's `performSearch` and `performGenreSearch` read `navigator.items[size - 2]`, so the action is silent whenever the series was reached from history, updates, a deep link or a related hop, which is most of the ways you get there. Ours uses `popUntil`, and a library search walks past any catalogue so it always lands on the library. Komikku took the same divergence first. Both details screens and the genre fallback walk through one kernel, `searchLibraryFromDetails` beside `searchGenreFromDetails` in `DetailsGenreSearch.kt`, called from `// RK` in `MangaScreen`. A sync that brings an upstream rewrite of these two functions should keep the walk.
- **The details screen's WebView, Share and Copy link hide when the extension gives the series no address, where Mihon shows them for every web source.** Mihon asks `getMangaUrl` on each tap: WebView and Share then do nothing when it throws, and Copy link calls it unguarded, so a throwing extension crashes the app. Ours resolves the viewed member's page once in the model (`EntryWebPage`, `Manga.webPageIn`, off the main thread and only when the member changes), and every action, the assistant link included, reads that page, so nothing is a silent no-op and Copy link cannot throw. Novels have always behaved this way. `MangaScreen`'s `getMangaUrl`, `openMangaInWebView`, `shareManga` and `copyMangaUrl` are gone under `// RK` notes; a sync touching them belongs in `rememberEntryWebActions`.
- **The header's long-press menus have no upstream counterpart at all.** Mihon has no menu: every long-press copies, and the source row has none. So there is nothing to conflict with, but a syncer reading `EntryInfoBox` against Mihon's header will find four handlers that no longer match. The source row deliberately offers Browse and copy rather than the two searches, because searching for a source's own name is the behaviour being removed and on a merged entry the name is a label.
- **`DownloadManager.deleteChapters` does not ask the categories excluded from removal, where upstream filters every delete through them.** Upstream's `getChaptersToDelete` runs inside `deleteChapters`, so a Delete the user tapped on a read chapter in an excluded category does nothing. Ours keeps only the bookmark check there (`deletableDownloads`), and automatic removal filters first: `DeleteDownload.awaitAll` (the mark-read delete) calls `deleteRemovableChapters`, and the reader's delete filters in `enqueueChaptersToDelete` as upstream's does. A sync that adds a new automatic caller of `deleteChapters` must point it at `deleteRemovableChapters`. Record in [downloads.md](subsystems/downloads.md).
- **`DownloadWorker` waits out a missing network, where upstream's worker stops the downloader and fails.** Upstream errors the chapter in flight, posts a warning and leaves the queue for a manual resume, both when a queue starts without a suitable network and when one drops mid-download. Ours pauses the downloader (`Downloader.stop(reason)` re-queues and posts the Paused notice through `DownloadNotifier.onNetworkPause`, on the worker's own id, in place of a user pause's notice and saying why it waits through an `// RK` reason parameter on `onPaused`, pinned by `PausedNoticeConformanceTest`), keeps polling, and starts it again once the issue clears, but only when the worker paused it, so a reorder's own pause and restart are left alone. A user pause or an emptied queue ends the wait, since `stop()` clears `isPaused`. A changed issue pauses again, so the notice never says Wi-Fi once the device is offline. `getForegroundInfo` (`// RK`) shows that same notice (`DownloadNotifier.pausedNotification`) for a worker that starts paused, because WorkManager's service can post the foreground notice after the downloader's own, and each pause in the wait loop calls `setForegroundSafely` again, so a first notice the service posts after a pause right at the start is covered by the paused one. Three `// RK` islands in `doWork`, plus the queue-restore wait, and `networkIssue` asks the shared `downloadNetworkIssue` rule the novel drain asks too (`// RK`); a sync hand-merges around them. The novel drain waits the same way; pinned by `NetworkWaitConformanceTest`, with the worker's own part in `DownloadWorkerTest`.
- **Work queued under a retired `*Job` class name still runs, where upstream drops it.** WorkManager stores each request's worker class name, and mihon `db45dda52` renamed its six `*Job` workers `*Worker` (Reikai renamed its own eight with them). Upstream installs no `WorkerFactory`, so a one-shot request queued before the upgrade (a resumed download, a pending tracker sync) fails to build and is dropped with a log line, and only the two periodic jobs its `Migration.ALWAYS` setups re-enqueue come back. Ours installs `reikai.data.work.RenamedWorkers` in `App.workManagerConfiguration`'s `// RK` island, which builds each of the 14 retired names as its renamed class, so nothing is dropped, `WorkerStartFailures` posts no notice for it, and a periodic job with no setup migration (`TrackerLibraryRefreshWorker`) keeps running. Pinned by `RenamedWorkersTest`.
- **Emptying a paused manga queue ends the downloader, from every path that empties it.** Upstream's `DownloadManager.removeFromDownloadQueue` stops the downloader only when it was running, and `deleteManga` and `renameManga` call `Downloader.removeFromQueue(manga)` directly, so a queue paused by a lost network (`Downloader.stop(reason)`, which `DownloadWorker` waits out for as long as the downloader stays paused) and then emptied kept the foreground worker until the next download. Ours calls the manager's `clearQueue` (clear plus stop) when a stopped queue is emptied, and both whole-manga paths go through `removeQueuedManga`, which removes by that rule; `Downloader.removeFromQueue(manga)` lost its last caller and is deleted. The novel drain ends by the same rule; record in [downloads.md](subsystems/downloads.md).
- **`DownloadManager.renameManga` leaves a folder it does not own.** Upstream moves the folder under the old title whenever the title changes, though another manga on the source with that title is named onto the same folder, and on scoped storage a new name another folder holds is dodged to "name (1)", which nothing finds. Ours asks `movesDownloadFolder` first, with the other titles on the source from `SourceTitlesRepository` (a constructor parameter, `// RK`), and leaves the folder in either case; the novel rename asks the same rule. A sync that changes `renameManga` keeps the island ahead of `removeQueuedManga`, so a folder that stays does not cost the manga its queue; record in [downloads.md](subsystems/downloads.md).
- **`UpdateMangaFromRemote` keeps a stored detail its source sends nothing for.** Upstream hands the source's author, artist, description and genres to `updateRemote`, which coalesces only a null, and writes the status outright, so a blank text field or an unknown status overwrites a known value. Ours passes each through the kernels the novel refresh calls (`keptDetail`, `keptGenres`, `keptStatus` in `KeptDetail.kt`), a null current value where the update coalesces and the stored status otherwise. A sync that changes the `MangaRemoteUpdate` built there keeps the island; record in [library.md](subsystems/library.md), pinned by `UnsentDetailConformanceTest`.
- **`HttpPageLoader.retryPage` always re-queues, taken from the open mihonapp/mihon#3770 ahead of upstream.** A sync that brings the merged PR in makes the `// RK` line a no-op to delete. **mihonapp/mihon#3813 (tap to retry in `WebGpuViewer`) is deliberately not taken while open**: Reikai's retry islands in that viewer cover it without its tap hit-testing, so a sync landing it must reconcile against them rather than stack both. Record: [reader.md](subsystems/reader.md).
- **`ReaderViewModel.preload` leaves a chapter whose preload just failed alone for 15 seconds, where upstream retries it on the next viewer trigger.** The rule is `ChapterRetryCooldown`, shared with the novel window. The three Retry buttons on a failed chapter (`PagerTransitionHolder`, `WebtoonTransitionHolder`, `WebGpuViewer.retryFailuresOnScreen`) pass `userAsked = true` to `preload` (through `ReaderActivity.requestPreloadChapter` in the first two) to skip it, so a sync touching any of those calls keeps the flag. Record: [reader.md](subsystems/reader.md).
- **A placeholder side of a `WebGpuViewer` spread takes its decoded partner's shape, where upstream sizes it as half the screen.** Upstream's `ProgressPage` and `ErrorPage` report `viewportPageWidth` by the viewport height whatever sits beside them, so a decoded page that is not itself shaped like half the screen draws too wide until its partner arrives. Ours keeps `viewportPageWidth` as the fallback and asks `placeholderSideWidth` (`WebGpuSpreadPlaceholder.kt`) first, with `buildSpreadPage` telling each placeholder its partner. Fenced `// RK`: the `SpreadPlaceholder` interface, the two `width` getters and three lines in `buildSpreadPage`. Drop the island if a sync brings an upstream fix. Record: [reader.md](subsystems/reader.md).
- **With Downloaded only on, the reader's skip-duplicate pass keeps a copy on disk, where upstream keeps one by scanlator and then drops it.** Upstream's `ReaderViewModel` runs `removeDuplicates` (the current chapter, then its scanlator's copy, then the first) and only afterwards `filterDownloaded`, so when the copy it kept is not on disk the chapter number vanishes from the reader although another copy is downloaded. Ours passes the on-disk set into the shared `navigableChapters` (`DuplicateChapters.kt`), which ranks a copy on disk first, then one a forward step may land on; the novel reader calls the same kernel. Fenced `// RK` in `navigable` and `onDiskIds`; pinned by `SkipDuplicateForwardConformanceTest` over both readers. Not reported upstream yet; drop the island if a sync brings an equivalent fix. Record: [reader.md](subsystems/reader.md).
- **`Throwable.formattedMessage` reads the first cause in the chain it has a message for, where upstream reads only the throwable it is handed.** OkHttp's `await` (`OkHttpExtensions.kt`) wraps every network failure in a bare `IOException` carrying the real one as its cause, so upstream never matches its own `UnknownHostException` branch for a source request, and an offline error shows the raw "Unable to resolve host" text instead of "No Internet connection". Fenced `// RK` in `ExceptionFormatter.kt` (`wordedCause`, walking the chain through `reikai.util.firstCause`, which the tracker error messages share), covered by `ExceptionFormatterTest`. `wordedCause` is also what Reikai's `sourceFailureMessage` reads to word an unworded browse or search failure as offline; the formatter itself keeps upstream's offline rule. Not reported upstream; drop the islands if a sync brings an equivalent fix.
- **A chapter push stamps a tracker's start date whenever it moves progress up from 0, where upstream stamps it only on chapter 1.** Upstream's rule sits in each dated tracker's `update` (`if (track.last_chapter_read == 1.0)` in `Anilist`, `Kitsu`, `MyAnimeList`, `MangaBaka`, `Hikka`), so a first push of any other chapter leaves the date empty. Ours is one clause in `reikai.domain.track.pushChapterProgress`, run before `update` for manga and novels, and the tracker files stay byte-close to upstream: their clause still fires on chapter 1 and writes the same day. The `// RK` island in `TrackChapter.await` hands the kernel the refreshed row and the chapter number, and the kernel reads the row's progress before writing the chapter onto it; a sync that touches that block must keep passing the unmodified refreshed row. Covered by `PushChapterProgressTest`. Drop the clause only if upstream moves the rule off `== 1.0` in every dated tracker.
- **`chapter` carries `chapter_remote_url_index`, an index upstream's table does not have.** Upstream has no query by url alone, so its `UNIQUE(manga_id, remote_url)` is enough there. Reikai's `getChapterByUrl` (`// RK`) backs the E-Hentai gallery-version reconciliation, which looks up every chapter of a gallery chain by url, once per chapter, and the unique index cannot serve that because it leads with the manga. The index is one `// RK` line in `chapter.sq` plus `56.sqm`, as Komikku's `idx_chapters_url`; a sync that rebuilds `chapter` must recreate it. Covered by `ChapterByUrlQueryPlanTest`.
- **`RefreshTracks` syncs a server tracker's progress into the chapters of the manga that owns the refreshed row, where upstream uses the manga it was asked about.** Upstream reads only that manga's own rows, so the two are always the same there. Ours reads the merge group through `GetTracksInGroup`, whose row for a tracker can sit on a sibling source, and a server tracker (Komga, Kavita, Suwayomi) numbers chapters by the source it serves, so marking the viewed source by its numbers marked the wrong chapters and never the right ones. Fenced `// RK` on the `syncChapterProgressWithTrack` call; with sharing off, or a row the viewed manga owns, it is upstream's call. Covered by `RefreshTracksTest`. Record: [tracking.md](subsystems/tracking.md).
- **A catalogue page that comes back empty after the first ends the list quietly, where upstream's `BaseSourcePagingSource` throws `NoResultsException` for any empty page.** Upstream's Browse then shows an indefinite "No results found" snackbar with Retry over results already on screen, and Retry only fetches the same empty page again. Ours runs each page through `CataloguePaging` (`reikai/domain/source/CataloguePaging.kt`), which the novel pager shares: an empty first load is still no results, an empty later one has no next key, and the source's `hasNextPage`, the dedupe by url and the refresh key stay upstream's. The `// RK` islands are the `paging` member, the `take` call and `getRefreshKey`; a sync hand-merges around them. Pinned by `CataloguePagingTest` and `SourcePagingSourceTest`. Record: [browse-and-sources.md](subsystems/browse-and-sources.md).
- **A missing-chapter marker counts only the numbers the series has nowhere, where upstream subtracts its two neighbours.** Upstream's divider and reader transition take `floor(higher) - floor(lower) - 1` over the rows shown, so a chapter a filter, Skip read or a hidden row drops reads as missing, and a repost or swapped pair reads as a gap of hundreds; its header adds the shown list's gaps. Ours asks `ChapterGap.Present`, each owner's whole numbers taken from every chapter before filters, hiding and the reader's skip passes, and the header counts each owner's number once. The islands are `MangaViewModel.chapterListItems` and `missingChapterCount`, the `gapPresent` state field, `ReaderChapter.gapPresent` (set in `ReaderViewModel.buildChapterList`), `calculateChapterGap` and `ChapterTransition`, which now asks it; a sync keeps them. Pinned by `ChapterGapTest`, `DetailsGapConformanceTest` and `ReaderChapterGapConformanceTest`. Record: [details.md](subsystems/details.md).
- **A chapter number the user corrected survives a sync, where upstream re-parses every number from the source on each refresh.** Upstream has no way to edit a number. Ours writes the correction on the chapter row and keeps it in `manga_chapter_number_override` (`58.sqm`), and the `// RK` island at the top of `SyncChaptersWithSource.await` puts each correction in place of the parsed number before the comparison, so an unchanged source writes nothing. A backup carries the source's own number in `BackupChapter` field 701 (`// RK`) beside Mihon's field 9, which holds the correction; `MangaBackupCreator.chapters`, `MangaRestorer`'s `RestoredManga` build, `RestoredManga.chapterNumberOverrides` and `RestoreRepositoryImpl.restore` carry it under `// RK`, and Mihon skips field 701. A sync keeps every island. Pinned by `ChapterNumberOverrideConformanceTest` and `ChapterNumberOverrideBackupTest`. Record: [details.md](subsystems/details.md).

- **`SearchToolbar` ignores an incoming query while its field has focus.** Upstream's state-based
  field reports every change outward and adopts whatever comes back, and what comes back is at least
  one report behind, so a keystroke landing inside that round trip is overwritten and lost. Typed at
  `adb input` speed, `shadowslave` arrives as `shwslav`. It needs no lagging
  screen, so it is not a Reikai-side state problem: Recents, whose query is written synchronously,
  dropped characters identically. The island is one focus flag plus a gate on the adopt branch; the
  `searchQuery == null` branch stays ungated so closing search still clears the field. Upstream's
  `AppBar.kt` was otherwise byte-identical, so re-apply the island rather than reverting to their
  blob. Drop it only if upstream fixes the race itself.

- **`GlobalSearchToolbar` gets no scroll behaviour on Global search or the migration search, where
  upstream's bar tints to the scrolled container colour as results scroll.** The parameter is a
  nullable `// RK` so the bar, the tab strip and the chip row read as one header block; both Reikai
  screens pass none, so the two search headers match each other. The migration search also draws an
  indeterminate bar through the `// RK` `isBusy` while a picked target resolves, in place of the
  searched-sources count. Upstream's `MigrateSearchScreen` is replaced by `EntryMigrationSearchScreen`
  (off-path manifest).
