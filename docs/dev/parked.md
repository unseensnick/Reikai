# Parked and not building

Items that were considered and set aside, with why and what would revive them. Kept out of
[ROADMAP.md](../../ROADMAP.md), which holds forward work only, so an entry here can carry its full
reasoning without turning the backlog into an essay. A dev record, so it may name sources.

Each entry: what it is, why it is parked or declined, the revive trigger, and a link to the plan doc
where one carries the detail. Reviving one means moving a one-line item back into the roadmap and
deleting it here.

- **Chapter translation for novels** `[XL]` - translate a novel chapter in place from inside the reader, the way tsundoku does with twelve engines behind a per-engine key. Parked (owner, 2026-09-03) rather than folded into the reader takeover: it is roughly 2400 lines across three modules, it is off by default in the reference, and it is wired into their forked reader model rather than sitting under the viewer, so it would widen the takeover without improving parity. Revive once the reader takeover has landed and there is demand for it. [Plan](plans/content-layer-reader-surface.md).
- **EPUB export for novels** `[L]` - export a novel, or a batch, as EPUB to a chosen folder. Parked (owner, 2026-09-03): in the reference it is not reachable from the reader at all, so it is a library and details feature rather than reader work, and it pulls in a full EPUB writer. Revive when someone has a use for it. [Plan](plans/content-layer-reader-surface.md).
- **Recover a source whose domain moved (mirror mode)** `[M-L]` - point an installed manga extension or novel plugin at a new domain. Parked until after Road B (owner, 2026-09-17), a condition Road B closing has now met, so it is the owner's to revive. Grounded design: override the domain in place, keeping the library attached, rather than tsundoku's separate mirror source, which needs a migration and still rewrites hosts underneath: one host-rewrite application interceptor on the shared client ahead of the Cloudflare step (URL, Referer and Origin, and the response URL mapped back, since the Madara and LightNovelWP plugin templates reject a host that differs from the one they asked for), plus a site override inside the plugin host's loadPlugin and rewritten WebView and share links. Confidence about 75% until a prototype runs against a moved site on OkHttp 5; known limits include extensions that build their own client, host-keyed rate limits going quiet, and absolute links a site now serves being stored.

- **Give backups a format version** `[M]` - stamp the format so a restorer can tell an old file from a current one. Parked (owner, 2026-09-16): exactly one call site would consult it, the novel category sort-flag translation in `NovelRestorer`, and the only reachable instance of that bug was the Yokai import, since removed. The residue itself stays open, so a pre-unification backup restored through the normal path still swaps a novel category's Downloaded and Tracker score sorting; revive when a second consumer appears, which any real format change would create. [Plan](plans/category-schema-unification.md).
- **Carry a merge group's source order and ranking override through a backup** `[M]` - let a restored group keep the hand-set manage-sources ranking the backup was taken with. Not building (owner, 2026-09-16): carrying it means reversing the recorded rule that restore prefers the local group's order and flag, and a backup is usually older than the device it lands on, so the failure mode is wiping an ordering the user set with nothing to undo it. A false flag never reaches the wire either, so an old backup and a deliberate Reset-order cannot be told apart; revive if restoring onto a fresh device turns out to want its ordering back. [Plan](plans/merge-component-consolidation.md).

- **Per-entry disable-auto-update** `[M]` - a per-series switch stopping the library update from touching it. Not building (owner, 2026-09-18): match Mihon, which has no such switch (Komikku adds one as an entry in the fetch-interval wheel). The earlier reasons were wrong: novels do keep a fetch interval and share that dialog, and its wheel is editable in the FOSS and nightly builds, since only the plain release build type hides it, as upstream does. Revive if Mihon adds one.
- **MyNovelList tracker** `[M]` - a fourth light-novel tracker over a documented `/api/v1` with a self-issued `Bearer` key. Not building (owner, 2026-08-25): the service is IReader's own deployment of a one-star repo created and abandoned on 2025-12-31, its shared catalogue holds zero entries, so search can never return a hit and every bind would have to create the entry first, and it is unrelated to the far larger site of the same name, which has no API at all. Revive if the catalogue fills and the service shows signs of maintenance. [Plan](plans/novel-specific-trackers.md).

- **Fold the follows screen into the shared catalogue** `[S]` - the one browse screen still drawing chrome of its own, and dispatching its dialogs off the manga model rather than the shared neutral set, so a new shared dialog case misses it. Not building (owner, 2026-08-28): folding it means two flags in shared chrome whose only job is to blank that chrome. Revive if the duplicated dialog dispatch starts costing real parity work, or if the shared catalogue grows a case the follows screen visibly lacks. [Plan](plans/content-layer-browse-surface.md).
- **Paged mode for the WebView novel reader** `[L]` - turn pages sideways instead of scrolling, with swipe-to-turn and a drag distance to commit, as tsundoku has. Parked as maybe later (owner, 2026-09-14): the web reader assumes vertical scrolling in its progress, fits and end-seen checks, place holding, taps, glide, auto-scroll, read-aloud and seek, and tsundoku's version reloads the document at every chapter edge, so it turns seamless chapters off rather than sharing the window. Revive if sideways paging is asked for. [Plan](plans/content-layer-reader-surface.md).
- **Reading status bar for manga and novels** `[M]` - a strip showing the time, battery, chapter and progress while reading, with a screen to reorder its parts, as tsundoku has for novels. Parked as maybe later (owner, 2026-09-14): nothing ties it to novels, so it would land for both readers, and it replaces nothing a reader is missing today. Revive if a status readout is asked for beyond the existing progress indicator. [Plan](plans/content-layer-reader-surface.md).
- **In-reader text edit mode for novels** `[L]` - fix a chapter's text by typing into it while reading. Parked as maybe later (owner, 2026-09-14): tsundoku's version saves the processed page over the downloaded chapter, which here would apply regex rules and auto-split twice and be lost on re-download, so a real version needs a stored per-chapter edit applied before those rules. Revive if fixing source typos in place is wanted. [Plan](plans/content-layer-reader-surface.md).
- **Quotes for novels** `[M]` - save a selected passage from the text-selection menu, then list, copy, share and delete saved passages. Parked as maybe later (owner, 2026-09-14): it is useful mainly with a jump back to the passage, which neither renderer can do yet, and tsundoku's version has neither that nor backup. Revive if collecting passages is asked for. [Plan](plans/content-layer-reader-surface.md).
- **Take the light-novel plugin chain off eager ViewModel construction** `[M]` - ten ViewModels and adapters take `LnPluginInstaller` as a plain constructor parameter, so opening any novel surface builds the installer, loader, source manager and plugin host on whatever thread composes the screen. Every one of them uses it only from a coroutine, so a `() -> LnPluginInstaller` parameter would fit, the way `NovelSourceManager` already does it. Parked: this is the shape that let a blocking constructor reach the UI as an ANR, but the blocking call itself is gone, so the chain now builds in microseconds and the conversion fixes no defect. Revive if another dependency in that chain gains real construction cost. [Plan](plans/novel-plugin-host.md).
- **Merged "All" view can drop a manga chapter present in one source (watch item)** `[S]` - the novel cause is fixed; the manga variant is number-dedup dropping an unmatchable sibling or a false collision, both intended tradeoffs, so it needs a concrete repro to tell a real bug from working-as-designed. See [merge-system-rebuild.md](plans/merge-system-rebuild.md).
- **Denormalize the library count columns** `[M]` - keep unread, read, total and bookmark counts as trigger-maintained columns instead of aggregating them on every library rebuild. Not building (owner, 2026-09-17): measured on the Fold, a whole-library recount takes about 70 ms and a library update re-ran it 343 times in 90 seconds, all off the main thread, so the gain is rarely felt, while the change patches a Mihon view, needs a migration and trades counts that are always recomputed for ones a missed trigger can leave wrong. Revive if scrolling during an update feels heavy and throttling the rebuild (the next item) does not fix it.
- **Library rebuilds in full on every download tick** `[S]` - neither download cache throttles its change signal, so each cache invalidation drives a whole library rebuild; throttling the tick where the library consumes it is the cheap fix. `LibraryViewModel`'s favorites flow also recomputes the EXH tag + alt-title reads inside that same combine (hoisting them is riskier, it touches Mihon's core favorites flow). Revive if rebuild cost shows on device; denormalizing the count columns (not building, above) is the heavier alternative.
- **Cut the details screen's per-load-step recompositions (Compose-stability optimization)** `[M]` - the only lever for the debug-build open-lag on huge (1000+) chapter lists: stop the ~6 per-open state emissions each recomposing the whole details screen. Parked because the lag is inherent debug-mode Compose, absent in release/preview, so the fix is uncertain stability work on the shared screen. Revive only if it also helps release.
- **Full two-way EH favorites sync** (pull account -> library) - the only feature that would mutate the library from a remote source; the scoped one-way backup shipped instead. Revive only if account -> library mirroring is wanted; the **EH per-page add-path throttle** `[S]` bundles here (redundant with the shipped 3/sec rate limit, which only this feature's sustained walk would exercise).
- **Manga per-page chapter loading** - no manga source would feed a paged chapter list (the contract returns the full list in one call).
- **Auto-error a chapter stuck mid-download** `[S]` - a per-chapter stall timeout so a hung image download gives up faster than `callTimeout` x3 (~8 min worst case). Parked: the pause/resume fix covers the reported bug and stalls still self-resolve via `callTimeout`. Revive if a permanent stall (callTimeout never fires) turns up.
- **Refresh trackers as part of the library update** `[S]` - the manual "Refresh tracker data" action shipped; folding it into the scheduled library update was deliberately not done. A chapter update runs per source on a schedule, while this is one network call per bound tracker per entry against rate-limited services, so attaching it would multiply every update's remote traffic invisibly. Revive if the manual action turns out to be something you run often enough to want automated, ideally behind its own preference and its own interval.
- **Hardcover / MiraiList trackers** - still no sanctioned read+write API; recheck Hardcover if it leaves beta. The novel-specific trackers are recorded in [novel-specific-trackers.md](plans/novel-specific-trackers.md). See [novel-tracking.md](plans/novel-tracking.md).
- **Novel recommendations / related carousel** - now feasible (trackers shipped) as an `[M]`; the source-native path stays infeasible (no plugin `getRelated`). Reconsider if wanted.
- **On-device novel translation (translation-engine ecosystem)** - tsundoku's pluggable translate stack (LibreTranslate / OpenAI / local Ollama / DeepL / Gemini / a custom-HTTP engine, plus a translate-on-download hook). Cool and possibly useful, but uncertain whether it gets real use; low priority, deliberately kept off the active backlog for now. Revive if on-device / AI novel translation is wanted.
- **History time grouping** `[M]` - group History by series within a week or day bucket, with the other chapters read in that bucket behind an expander, the way Yokai did. Parked because Reikai's History already collapses to one row per entry in SQL and draws day headers, so the expander would mean un-collapsing the history query to return read records again, for an affordance nobody has asked for. Revive if one row per series per period turns out to be what is wanted. [Plan](plans/content-layer-recents-surface.md).
- **Widen the taste profile past its five trackers** `[M]` - feed the recommendation taste profile from more of the bound trackers than the five it reads today. Parked: MD's list tracker is ruled out (owner, 2026-08-23), MangaUpdates is out on cost and the three self-hosted trackers on merit, leaving MangaBaka and Hikka, whose granted OAuth scopes (`library.read`, `readlist`) imply a readable list that nothing in the tree calls, so the work would start by confirming an endpoint exists at all. Revive if either turns out to expose a list endpoint carrying tags without a second per-title series call, the cost that ruled MangaUpdates out. The plan below is a removed-feature record now, kept because it carries the per-tracker API measurements this item rests on. [Plan](plans/recommendations-adult-content.md).

- **CMK source-native recommendations (+ id-graph)** - stock CMK was pulled from the extension repos, so the recs port's id-set gate never fires (only clones with different ids remain). Revive if a first-party CMK source returns; the id-graph idea (suggest tracker binds from an entry's cross-links) rides the same API.
- **MD source-native similarity carousel** - its only data source (`api.similarmanga.com`, the TF-IDF `similar-manga` project) is frozen at 2025-05-27 and unmaintained; MD's official `/relation` endpoint returns exact relations (doujinshi / colored), not discovery, and tracker recs already cover popular titles. Dropped with the MD enhanced source (0.2.0); see [md-enhanced-source.md](plans/md-enhanced-source.md).
- **Serialize track-sheet edits (rapid edits clobber each other)** `[M]` - each field edit runs in its own coroutine (`EntryTrackInfoDialog.kt`, the shared manga+novel dialog), so two quick edits race on the same track row and the second wins. A Mihon-wide race, worst on MDList, now applying to both content types. Parked because the per-track mutex touches shared tracker code; revive standalone.
- **Content-type binary fetch for LN plugins** - auto-detecting a binary response and base64-transporting it would let a plugin read true binary bytes from a normal `fetch`, but it risks garbling a mislabeled non-UTF-8 (GBK / Shift-JIS) text source, and no current plugin fetches raw binary (they decode base64 / hex text via the shipped `Buffer` shim). Revive with an explicit opt-in binary mode if a real binary-fetch source appears.
- **No-code custom novel source (CSS-selector wizard)** `[L]` - add a whole novel site from JSON config with a per-step test-probe wizard, no plugin authoring (tsundoku's `CustomNovelSource` + `CustomSourceManager.testSource`, ~4000 lines with its editor screens). Parked 2026-08-02: large, orthogonal to the content-layer program, and unproven demand. Revive if hand-adding sites the plugin ecosystems lack becomes a real ask.

- **Tune the auto-webtoon source-name catch-alls** `[S]` - the classifier takes Komikku's token lists verbatim, and only the two generic catch-alls are worth touching (they force webtoon mode on mixed-content aggregators and at least one page-format western comic host). Still parked, but the old reason (identical lists keep a library reading the same in both apps) is now only half true: the classifier votes across every member of a merge group, which Komikku cannot do, so a merged library already reads differently. Revive if a real false positive annoys. [Plan](plans/auto-webtoon-mode.md).
- **Cross-app preference-key compatibility with Komikku** `[M]` - Reikai shares none of Komikku's sixteen `eh_*` preference keys, so a backup restored in either direction silently drops EH logins, saved searches and the rest of the adult-source settings (preferences back up by raw key, so adopting the upstream names would close the gap). Parked because renaming live keys resets existing users' settings without a migration, and it is unproven how many people move between the two apps. Revive if switching apps should be seamless.
